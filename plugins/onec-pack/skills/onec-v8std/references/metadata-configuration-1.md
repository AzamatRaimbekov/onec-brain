## Организация работы конфигурации

### std413 Использование параметров сеанса - [its](https://its.1c.ru/db/v8std/content/413/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Назначение: значения на время жизни клиентского сеанса (текущий пользователь, флаг обмена, рабочее место).
  Основное применение - запросы и ограничения доступа (RLS) текущего сеанса.
- Чтение/запись `ПараметрыСеанса.Имя` из кода требует у пользователя права на этот параметр; в тексте
  ограничения доступа право не нужно.
- Не хранить в параметрах сеанса данные только для клиентской логики: они живут на сервере, каждое обращение
  с клиента = серверный вызов. Для клиента - глобальные переменные модуля управляемого (обычного) приложения.
- Не кешировать в них вычисленные значения для серверной логики - для этого серверный общий модуль с
  повторным использованием возвращаемых значений (`...ПовтИсп`). Исключение: расчет занимает время,
  сопоставимое с периодом сброса платформенного кеша.
- Не инициализировать все параметры при старте программы (не все нужны; код может их сбрасывать).
  Устанавливать «по требованию» в обработчике `УстановкаПараметровСеанса` модуля сеанса - в момент первого
  обращения к неустановленному параметру.
- Параметры, вычисляемые из одних и тех же данных, ставить группой и вести список уже установленных, чтобы не
  инициализировать повторно.
```bsl
Процедура УстановкаПараметровСеанса(ИменаПараметровСеанса)
	Если ИменаПараметровСеанса = Неопределено Тогда
		Возврат; // старт сеанса: только то, что действительно нужно сразу
	КонецЕсли;
	Установленные = Новый Массив;
	Для Каждого Имя Из ИменаПараметровСеанса Цикл
		Если Установленные.Найти(Имя) = Неопределено Тогда
			УстановитьПараметр(Имя, Установленные); // сам добавляет в Установленные всю группу
		КонецЕсли;
	КонецЦикла;
КонецПроцедуры
```
- См. также: влияние изменения параметров сеанса и ФО на производительность RLS.

### std467 Общие требования к конфигурации - [its](https://its.1c.ru/db/v8std/content/467/hdoc)
Стандарт; управляемое, мобильное, обычное приложение (п.1.2-1.4 - управляемое и обычное).
- 1.1 Использовать только штатные документированные возможности платформы.
- 1.2 Работать одинаково на всех поддерживаемых платформой СУБД, ОС, браузерах и режимах. В веб-клиенте все
  ключевые функции доступны без расширения работы с файлами; взаимодействие с пользователем - асинхронное.
- 1.3 Проверка конфигурации (Конфигурация - Проверка конфигурации) не должна давать ошибок. Допустимые
  обоснованные исключения: обработчики событий формы, подключаемые из кода; ограничения на модальность и
  синхронные вызовы; ограничение на флаг «Вызов сервера»; несущественные предупреждения (std759).
- 1.4 Поддерживать запуск в режиме обычного приложения (толстый клиент) и внешнего соединения для
  администраторов (полные права) - ради совместимости со старыми внешними отчетами/обработками. Для этого:
  свойство «Использовать управляемые формы в обычном приложении» = Истина, «Использовать обычные формы в
  управляемом приложении» = Ложь; общие модули - по схеме std469; в Конфигураторе редактировать для обоих
  режимов (Сервис - Параметры - Общие). Отказ - только в обоснованных случаях.
- 1.5 Не отходить от умолчаний платформы (тех. решения, интерфейс, отчеты) без обоснования; учитывать
  ограничения на использование внешних ресурсов.
- 2.1 Имена, синонимы, комментарии, любые тексты для пользователя или разработчика - грамотным русским языком.
- 2.2 Нет неиспользуемых объектов метаданных и кода (модулей, процедур, переменных), если они не нужны ни
  конфигурации, ни интеграциям.
- 2.3 Объекты верхнего уровня (справочники, документы, общие модули...) сортировать в дереве по имени;
  подчиненные (реквизиты, измерения, формы) - по логике проекта. Исключения из сортировки: общие
  реквизиты-разделители (порядок = порядок установки параметров сеанса), объекты с префиксом `Удалить`
  (`Obsolete`) - в конец ветки, группы команд (порядок влияет на командную панель).

### std469 Правила создания общих модулей - [its](https://its.1c.ru/db/v8std/content/469/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Модуль группирует процедуры одной подсистемы или одного назначения (продажи; работа со строками).
- Выбирать ровно один из четырех видов:

| Вид | Пример имени | Вызов сервера | Сервер | Внешнее соед. | Клиент (обычное) | Клиент (управляемое) |
|-----|--------------|:-:|:-:|:-:|:-:|:-:|
| Серверный | `ОбщегоНазначения` (`...Сервер`) | | + | + | + | |
| Серверный для вызова с клиента | `ОбщегоНазначенияВызовСервера` | + | + | | | |
| Клиентский | `ОбщегоНазначенияКлиент` (`...Глобальный`) | | | | + | + |
| Клиент-серверный | `ОбщегоНазначенияКлиентСервер` | | + | + | + | + |

- Серверный: вся внутренняя серверная логика, недоступна клиенту. Флаги Сервер (без Вызова сервера) +
  Клиент (обычное приложение) + Внешнее соединение - так можно передавать мутабельные параметры
  (`СправочникОбъект`, `ДокументОбъект`): подписки на события, процедуры, получающие объект из модулей
  объектов. Имя - по общим правилам (`РаботаСФайлами`); постфикс `Сервер`/`Server` только при конфликте с
  глобальным контекстом (`РегламентныеЗаданияСервер`).
- Вызов сервера: клиентский API сервера; флаг Сервер + Вызов сервера; постфикс `ВызовСервера`/`ServerCall`
  обязателен. Экспортные методы НЕ принимают и не возвращают мутабельные типы (их нельзя передать клиенту).
- Клиентский: флаги Клиент (управляемое) + Клиент (обычное); иная комбинация - только если код нужен лишь в
  одном режиме. Постфикс `Клиент`/`Client`.
- Клиент-серверный: одинаковый код для клиента и сервера; флаги Клиент (управляемое) + Сервер (без Вызова
  сервера) + Клиент (обычное) + Внешнее соединение. Постфикс `КлиентСервер`/`ClientServer`.
- Не ветвить клиент-серверный модуль инструкциями препроцессора: разную для клиента и сервера логику выносить
  в модули соответствующего вида (модулей станет больше - это нормально). Модули форм и команд - особый
  смешанный случай, там разделение в одном модуле допустимо.
- Имя модуля = имя подсистемы/механизма; избегать слов «Процедуры», «Функции», «Обработчики», «Модуль»,
  «Функциональность» без крайней нужды.
- Уточняющие постфиксы:
  - `Глобальный`/`Global` - для глобальных модулей, без `Клиент` (`...СлужебныйГлобальный`);
  - `ПолныеПрава`/`FullAccess` - флаг Привилегированный;
  - `ПовтИсп`/`Cached` и `КлиентПовтИсп`/`ClientCached` - повторное использование значений (на время вызова
    или сеанса), сервер и клиент соответственно;
  - `Переопределяемый`/`Overridable`, `КлиентПереопределяемый`/`ClientOverridable` - в библиотеках, методы,
    реализацию которых меняет потребитель;
  - `Локализация`/`Localization`, `КлиентЛокализация`/`ClientLocalization` - национальная специфика в
    локализуемых конфигурациях.

### std470 Использование функциональных опций - [its](https://its.1c.ru/db/v8std/content/470/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Необязательную функциональность включать/выключать функциональной опцией (ФО); значение хранить в данных
  ИБ (константа, ресурс регистра сведений, реквизит справочника) - указать в свойстве «Хранение».
- Объекты метаданных включать в состав ФО - платформа сама скрывает интерфейс. В коде -
  `ПолучитьФункциональнуюОпцию("Имя")`. ФО бывают не только Булево (ссылка, перечисление и т.п.).
- Зависимость от контекста (например, по организации): параметр ФО + регистр сведений с измерением, ресурс в
  «Хранение», у параметра в «Использование» - измерение. В форме:
  `УстановитьПараметрыФункциональныхОпцийФормы(Новый Структура("Организация", Орг))`; в коде - второй
  параметр `ПолучитьФункциональнуюОпцию`.
- Не применять ФО не по назначению: ради видимости элементов одной формы (ФО - для всей конфигурации) и для
  кеширования данных на сервере (для этого модули `ПовтИсп`).
- Платформа не дает средств установки ФО: в конфигурации нужна своя форма/код для констант, справочников,
  записей регистров.
- Параметризованная ФО: нет записи для параметра - опция выключена; несколько записей - значения по «ИЛИ».
- Хранение в периодическом регистре: берется срез последних; для другой даты передать параметр `Период`
  (тип Дата), предварительно приведя к периодичности регистра (`НачалоМесяца(...)` для месячного). Параметр
  `Период` в метаданных НЕ создавать - он системный.
- После изменения значения ФО командный интерфейс сам не обновляется - вызвать `ОбновитьИнтерфейс()`.
- Значения ФО кешируются на сервере; большой кеш тормозит. Не параметризовать ФО многозначными данными
  (контрагент, товар) - параметризовать видом/признаком (перечисление `ВидКонтрагента`).
- Зависимые ФО: если функция нужна только при сочетании опций А и Б - завести отдельную ФО В, привязать
  объекты к ней (не к А и Б) и поддерживать ее значение кодом (например, при записи констант А и Б). В форме
  настроек показывать все три, В - только для чтения. Булевы ФО редактировать флажком с заголовком = имени ФО.
- Взаимоисключающие ФО - переключатель или поле со списком; заголовки/значения = названия ФО.
- Мелкую функцию со сложной зависимостью и без понятного пользователю названия не оформлять отдельной ФО -
  управлять элементами формы кодом в `ПриСозданииНаСервере` по значениям существующих ФО.
- Не более 10 параметров ФО на конфигурацию. Не плодить параметры одного смысла/типа (один
  `ТипОбъектаКонфигурации`, связанный с измерениями нескольких регистров, вместо двух разных).
- Порядок проектирования: выявить опциональные функции - решить, один «выключатель» на ИБ или по разрезам -
  составить список ФО и параметров (без дублей по типу) - при избытке ранжировать параметры по охвату и
  важности, убрать слабые - оставшиеся без параметра ФО сделать непараметризованными или удалить.

### std480 Оформление карты маршрута бизнес-процесса - [its](https://its.1c.ru/db/v8std/content/480/hdoc)
Стандарт; управляемое и обычное приложение.
- Рисовать сверху вниз (иная ориентация - если так нагляднее). Сетка с шагом 20 точек, отображается линиями.
- Без жирных и цветных шрифтов. Минимум изгибов линий (по возможности один), подгоняя размеры и положение
  точек.
- Отступ одна клетка от левого и верхнего края. Ширина точек - четное число клеток; пропорции точек и
  декораций близки к спичечному коробку (например 3x6), без сильно вытянутых фигур.
- Текст в точках и декорациях по центру; комментарии - по левому краю. Не пересекать границы печатного листа
  (Графическая схема - Режим просмотра страниц).
- Старт и Завершение: 2x2 клетки, без наименования, количество - по логике; отступ до соседней точки 2 клетки.
- Действие / Автоматическая обработка / Вложенный бизнес-процесс: размер по тексту; текст - короткая директива
  «что сделать» («Выписать счет», не «Выписка счета»). Слева - входящие данные, справа - результаты.
- Входящие документы - слева на 2 клетки, исходящие - справа на 2 клетки; пунктир со стрелкой; фигура
  «Документ», пропорции близки к А4 (4x5, 3x4 клетки).
- Комментарии: фигура «Скобки вертикальные/горизонтальные» в 2 клетках слева (к входящему) или справа (к
  исходящему), пунктир без стрелки к грани точки.
- Условие: короткий вопрос с «?», ответ только Да/Нет («Счет есть?»); точка компактная; входящие и исходящие
  линии суммарно не короче 2 клеток, чтобы читались «Да»/«Нет».

### std543 Использование подсистем - [its](https://its.1c.ru/db/v8std/content/543/hdoc)
Методическая рекомендация; управляемое и обычное приложение.
- Подсистемы решают две задачи: глобальный командный интерфейс (разделы) и группировка объектов для
  разработки (отбор в дереве, перенос, область поиска). В простом случае структуры совпадают; у таких
  подсистем флажок «Включать в командный интерфейс» установлен.
- Для логической группировки по функциям завести отдельную иерархию «функциональных» подсистем со снятым
  флажком «Включать в командный интерфейс» (например, `Номенклатура` в функциональной НСИ, но видна в
  разделах НСИ и Маркетинг).
- Общие модули, регламентные задания, константы, подписки на события и прочие объекты без представления в
  интерфейсе включать только в функциональные подсистемы.

### std550 Имена объектов метаданных в конфигурациях - [its](https://its.1c.ru/db/v8std/content/550/hdoc)
Стандарт; управляемое, мобильное, обычное приложение (отдельные строки - только управляемое/обычное, помечены
«УО»; интерфейсы и стили - только обычное). Везде: не включать слова, без которых смысл не меняется
(«Справочник…», «Документ…», «Форма…», «Макет…», «Константа…», «Отчет…», «Обработка…» и т.п.).

| Вид | Правило | Пример |
|-----|---------|--------|
| Подсистемы (УО) | общие правила | `Финансы`, `Маркетинг` |
| Общие модули | по std469 | |
| Параметры сеанса | общие правила | `ТекущийПользователь`, `ОбменДаннымиВключен` |
| Роли | «прикладные» - по должности; «мелкие» - по разрешаемому действию | `Бухгалтер`; `ДобавлениеИзменениеНСИ` |
| Общие реквизиты (УО) | общие правила | |
| Планы обмена | РИБ - кратко правило синхронизации; между конфигурациями - Обмен+Источник+Приемник, имя одинаково в обеих; с версиями - номера редакций в имени | `ПоОрганизациям`; `ОбменУправлениеТорговлей110РозничнаяТорговля10` |
| Критерии отбора (УО) | множественное число, от отбираемого списка | `СвязанныеДокументы` |
| Подписки на события | от сути действия, глагол в инфинитиве | `ПроверитьИзменениеРеквизитовОбъекта` (не `ЗапретРедактирования...ПередЗаписью`) |
| Регламентные задания (УО) | единственное число, от существительного | `УведомлениеИсполнителейОНовыхЗадачах` (не `Уведомить...`) |
| Функциональные опции | от описания включаемой функциональности | `ИспользоватьВерсионированиеОбъектов`, `ПрефиксИнформационнойБазы` |
| Параметры ФО | от описания параметра; не обязано совпадать с реквизитом | `Организация`, `ТипОбъектаКонфигурации` |
| Определяемые типы (УО) | единственное число, от назначения; не как имена типов (`Строка`, `Число`), без «Тип…», «Объект…», «Ссылка…» | `АртикулНоменклатуры` (не `Строка25`), `КонтактВзаимодействий` |
| Хранилища настроек (УО) | общие правила | `ХранилищеВариантовОтчетов` |
| Общие формы | существительное; без «Форма», «Окно», «Диалог» | `НастройкаСистемы`, `ВыборОбъектовМетаданных` |
| Общие команды | в панели навигации - по открываемому списку; иначе - глагол в инфинитиве | `ЗадачиПоБизнесПроцессу`; `ВыполнитьСопоставление` |

### std556 Начальные действия при работе конфигурации - [its](https://its.1c.ru/db/v8std/content/556/hdoc)
Стандарт (п.2-3 - методическая рекомендация); управляемое, мобильное, обычное приложение.
- Конфигурация сама распознает первый запуск (начальное заполнение минимумом данных) и первый запуск нового
  релиза (обновление данных ИБ). С БСП - только через подсистему «Обновление версии ИБ»; требования ниже - для
  конфигураций без БСП.
- (Рек.) Делить начальное заполнение на обязательное и облегчающее старт; после первого запуска / обновления
  показывать администратору описание конфигурации или изменений версии.
- Неполную обработку контролировать: предупреждение пользователю, подробный протокол - в журнал регистрации.
- РИБ: обновление данных в подчиненном узле выполнять после загрузки уже обновленных данных из главного и
  делать идемпотентным - повторный прогон не создает и не меняет данные повторно. Иначе новые объекты
  размножатся по всем узлам, а изменения уйдут обратно в главный узел лишним трафиком.
```bsl
// Создаем предопределенный профиль только если его еще нет
Запрос = Новый Запрос("ВЫБРАТЬ ПЕРВЫЕ 1 ИСТИНА ИЗ Справочник.ПрофилиГруппДоступа
	|ГДЕ Наименование = &Имя И Предустановленный");
Запрос.УстановитьПараметр("Имя", ИмяПрофиля);
Если Запрос.Выполнить().Пустой() Тогда
	Профиль = Справочники.ПрофилиГруппДоступа.СоздатьЭлемент();
	Профиль.Наименование = ИмяПрофиля;
	Профиль.Предустановленный = Истина;
	Профиль.Записать();
КонецЕсли;
```

### std557 Работа с пользовательскими настройками - [its](https://its.1c.ru/db/v8std/content/557/hdoc)
Стандарт; управляемое и обычное приложение.
- Персональные настройки хранить только в `ХранилищеОбщихНастроек` (`Загрузить`/`Сохранить`). Не в
  регистрах, реквизитах, табличных частях, внешних файлах.
- Нужно право `СохранениеДанныхПользователя`.
- Каждой настройке - свой уникальный строковый ключ (`ОсновнаяОрганизация`, `ОсновнойСклад` раздельно).
  Объединять в структуру/массив/соответствие можно только то, что всегда читается и пишется вместе (параметры
  прокси: адрес, логин, пароль).
- Предусмотреть общее место редактирования всех настроек (общая форма «Мои настройки», пример - демо БСП);
  дополнительно отдельные настройки можно редактировать прямо на месте (флажок «больше не показывать» в
  подсказке).
- Формы и элементы для персональных настроек доступны только при праве `СохранениеДанныхПользователя`.
- Настройки не переносятся между узлами ИБ - при необходимости передавать кодом.
- Хранятся по строковому имени пользователя ИБ: при переименовании теряются, а новый пользователь со старым
  именем их получит. Переносить настройки при переименовании и очищать при удалении; в БСП - в
  `ПриЗаписиПользователяИнформационнойБазы` и `ПослеУдаленияПользователяИнформационнойБазы` модуля
  `ПользователиПереопределяемый`.

### std643 Работа в разных часовых поясах - [its](https://its.1c.ru/db/v8std/content/643/hdoc)
Стандарт; управляемое и обычное приложение.
- Конфигурация должна корректно работать, когда пояс сервера не совпадает с поясом пользователей (клиент-
  сервер, SaaS): операции - по местному времени пользователя.
- На сервере вместо `ТекущаяДата()` - `ТекущаяДатаСеанса()` (время в поясе сеанса).
- Нужна метка, не зависящая от пояса (момент перезаполнения кеша, время последнего запуска фонового
  задания) - `УниверсальноеВремя()`.
- Методы платформы, возвращающие локальное время сервера, приводить к универсальному или к времени сеанса:
```bsl
Универсальная = УниверсальноеВремя(ПолнотекстовыйПоиск.ДатаАктуальности());
ДатаСеанса = МестноеВремя(Универсальная, ЧасовойПоясСеанса());
```
- На клиенте `ТекущаяДата()` тоже запрещена (клиентское и серверное время не должны расходиться). Вместо:
  передавать дату сеанса с сервера; в документах использовать `Объект.Дата`; если дата не задана - передать
  `Неопределено` и вычислить `ТекущаяДатаСеанса()` на сервере в `ПриСозданииНаСервере`.
- С БСП в прочих клиентских случаях - `ОбщегоНазначенияКлиент.ДатаСеанса()`.
- Исключения (нужно именно время сервера) - только с обосновывающим комментарием у вызова.
- В одной процедуре не вызывать `ТекущаяДатаСеанса()` (`ТекущаяДата()`) несколько раз - значения разойдутся;
  получить один раз в переменную и переиспользовать.

### std677 Использование общих реквизитов - [its](https://its.1c.ru/db/v8std/content/677/hdoc)
Стандарт; управляемое и обычное приложение.
- Две задачи: разделение данных («Разделение данных» = Разделять) и добавление реквизита сразу многим
  объектам (= Не использовать).
- Без разделения - только для функциональности уровня всей конфигурации, не входящей в бизнес-логику объекта,
  но требующей хранения данных прямо в объектах.
- Не использовать общие реквизиты для удобства вместо обычных (`Ответственный`, `Комментарий`, `Организация`
  в документах - неправильно). Права на общий реквизит настраиваются отдельно от объектов.
- Порядок реквизитов-разделителей в дереве = требуемый порядок установки связанных параметров сеанса.
