## Работа с запросами

### std412 Упорядочивание результатов запроса - [its](https://its.1c.ru/db/v8std/content/412/hdoc)
Стандарт
- Ставить УПОРЯДОЧИТЬ ПО, если алгоритм зависит от порядка строк или результат так или иначе видит пользователь
  (заполнение ТЧ, отчеты). Без него порядок строк не определен и может меняться при смене СУБД, ее версии или
  настроек.
- Для запросов, формирующих движения, сортировать только если порядок - часть алгоритма (например, списание партий
  по FIFO); иначе не сортировать - лишняя нагрузка на СУБД.
- Поле, которое может быть NULL (например, из ЛЕВОГО СОЕДИНЕНИЯ), перед сортировкой оборачивать в ЕСТЬNULL - разные
  СУБД ставят NULL в разные места.
- Для показа пользователю сортировать по полям примитивных типов; вместо сортировки по ссылке - сортировать по ее
  строковому представлению (ПРЕДСТАВЛЕНИЕ), иначе порядок выглядит случайным.
- Не писать УПОРЯДОЧИТЬ ПО, если порядок не важен, результат не показывается или заведомо одна строка.
- С РАЗЛИЧНЫЕ сортировать только по полям из списка ВЫБРАТЬ: поля сортировки неявно попадают в выборку и дают
  "дубли".
- ПЕРВЫЕ вместе с АВТОУПОРЯДОЧИВАНИЕ запрещено. В остальных случаях АВТОУПОРЯДОЧИВАНИЕ не рекомендуется; допустимо
  только когда порядок не важен, но должен совпадать на всех СУБД, и причина пишется комментарием прямо перед
  текстом запроса.

```bsl
// ВЫБРАТЬ Товары.Ссылка КАК Товар, ЕСТЬNULL(Остатки.КоличествоОстаток, 0) КАК Остаток
// ...
// УПОРЯДОЧИТЬ ПО Остаток, ПРЕДСТАВЛЕНИЕ(Товар)
```

### std434 ОБЪЕДИНИТЬ и ОБЪЕДИНИТЬ ВСЕ - [its](https://its.1c.ru/db/v8std/content/434/hdoc)
Стандарт
- По умолчанию писать ОБЪЕДИНИТЬ ВСЕ. Простое ОБЪЕДИНИТЬ тратит время на схлопывание одинаковых строк даже когда их
  быть не может.
- ОБЪЕДИНИТЬ - только если устранение дублей действительно нужно для результата.

### std435 Ограничение на ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ - [its](https://its.1c.ru/db/v8std/content/435/hdoc)
п.1 - методическая рекомендация, п.2 - Стандарт
- На PostgreSQL ПОЛНОЕ СОЕДИНЕНИЕ сильно медленнее (особенно два и более в одном запросе). По возможности
  переписывать через ОБЪЕДИНИТЬ ВСЕ двух выборок (недостающие ресурсы = 0) + СГРУППИРОВАТЬ ПО ключу с СУММА.
- Если без полного соединения объективно не обойтись - оставить: платформа сама подменяет его на PostgreSQL
  эквивалентом с сохранением ПЕРВЫЕ/РАЗЛИЧНЫЕ/УПОРЯДОЧИТЬ ПО. Не переписывать "механически".
- Запрещено (п.2): одновременно ПОЛНОЕ СОЕДИНЕНИЕ и обращение к табличным частям в секции ВЫБРАТЬ (не переносится
  на PostgreSQL).

```bsl
// вместо План ПОЛНОЕ СОЕДИНЕНИЕ Факт:
// ВЫБРАТЬ ПФ.Товар КАК Товар, СУММА(ПФ.План) КАК План, СУММА(ПФ.Факт) КАК Факт
// ИЗ (ВЫБРАТЬ План.Товар КАК Товар, План.Сумма КАК План, 0 КАК Факт ИЗ ВТПлан КАК План
//     ОБЪЕДИНИТЬ ВСЕ
//     ВЫБРАТЬ Факт.Товар, 0, Факт.Сумма ИЗ ВТФакт КАК Факт) КАК ПФ
// СГРУППИРОВАТЬ ПО ПФ.Товар
```

### std436 Многократное выполнение однотипных запросов - [its](https://its.1c.ru/db/v8std/content/436/hdoc)
Стандарт
- Не выполнять однотипный запрос в цикле: собрать параметры в массив и выбрать все одним запросом (условие
  В (&Массив), ОБЪЕДИНИТЬ ВСЕ, пакет запросов).
- В БСП использовать "списочные" функции: ОбщегоНазначения.ЗначениеРеквизитаОбъектов вместо
  ЗначениеРеквизитаОбъекта в цикле; УправлениеКонтактнойИнформацией.КонтактнаяИнформацияОбъектов вместо
  КонтактнаяИнформацияОбъекта.
- Серия запросов допустима, если: единый запрос заметно сложнее разработать; единый запрос деградирует (например,
  виртуальные таблицы остатков/срез последних на разные даты); идет порционная обработка больших объемов
  (обработчики обновления, групповое проведение/изменение, удаление помеченных, контроль учета, загрузка из файлов
  и внешних источников, получение почты). Оправдание - запросы нужны для порционности, или незаметны на фоне
  записи, или неустранимы средствами платформы (чтение/запись наборов регистра по значениям измерения).
- Запросы к разным таблицам тоже желательно объединять (ОБЪЕДИНИТЬ ВСЕ/пакет), но выигрыш может быть мал.

```bsl
Запрос = Новый Запрос(
	"ВЫБРАТЬ
	|	Счета.Ссылка КАК Счет
	|ИЗ
	|	Справочник.БанковскиеСчета КАК Счета
	|ГДЕ
	|	Счета.Банк В (&Банки)");
Запрос.УстановитьПараметр("Банки", МассивБанков); // а не цикл с Банк = &Банк
```

### std437 Оформление текстов запросов - [its](https://its.1c.ru/db/v8std/content/437/hdoc)
Стандарт; п.2 (псевдонимы полей) - методическая рекомендация
- Все ключевые слова языка запросов - ЗАГЛАВНЫМИ.
- Явно задавать псевдоним каждому полю (Касса.Валюта КАК Валюта): при переименовании реквизита меняется только
  текст запроса, а не код обращения к выборке. Помнить, что поле "через точку" (Касса.Валюта.Наименование) без
  псевдонима получит имя ВалютаНаименование. Перед псевдонимом источника всегда писать КАК.
- Текст запроса многострочный и структурированный, даже короткий; в одну строку нельзя.
- Сложные запросы (вложенные, соединения, объединения) комментировать: зачем каждая таблица. Конструктор запросов
  молча удаляет комментарии.
- При создании объекта Запрос - комментарий, какие данные он получает.
- Программную сборку текста комментировать по этапам; каждая часть должна открываться конструктором запросов.
- Подстановку имени поля/таблицы делать через маркер в валидном тексте (&ИмяПоля, &Таблица, #Таблица) +
  СтрЗаменить, а не разрывом строки конкатенацией.
- Не держать ПОМЕСТИТЬ закомментированным с последующим раскомментированием; писать ПОМЕСТИТЬ в тексте и при
  необходимости вырезать его СтрЗаменить.
- Разделитель пакета ";" добавлять вместе со следующим запросом (или собирать массив текстов и СтрСоединить с
  разделителем), а не оставлять висящий ";" в конце условного фрагмента.

```bsl
ТекстЗапроса =
	"ВЫБРАТЬ
	|	Таблица.Наименование КАК Наименование
	|ИЗ
	|	&ТаблицаСправочника КАК Таблица";
ТекстЗапроса = СтрЗаменить(ТекстЗапроса, "&ТаблицаСправочника", "Справочник." + ИмяСправочника);

Тексты = Новый Массив;
Тексты.Добавить(ТекстПервогоЗапроса);
Тексты.Добавить(ТекстВторогоЗапроса);
Запрос.Текст = СтрСоединить(Тексты, ";" + Символы.ПС);
```

### std438 Проверка на пустой результат запроса - [its](https://its.1c.ru/db/v8std/content/438/hdoc)
п.1 - Стандарт, п.2 - Методическая рекомендация
- Проверять наличие строк методом РезультатЗапроса.Пустой(), а не через Выбрать()/Следующий() или Выгрузить() -
  выборка стоит дополнительного времени.
- Если результат все равно будет выбираться/выгружаться, предварительный Пустой() не нужен - просто цикл по
  выборке.

```bsl
Возврат Не Запрос.Выполнить().Пустой();
```

### std535 Округление результатов арифметики в запросах - [its](https://its.1c.ru/db/v8std/content/535/hdoc)
Методическая рекомендация
- Если порядки чисел известны, не делить малое на большое раньше умножения: 0.02 * A / B лучше, чем 0.02 / B * A.
- Платформа считает в запросах с точностью до 8 знаков дробной части, но на разных СУБД она может отличаться для
  деления, СРЕДНЕЕ и умножения дробных множителей. При расхождении применять ВЫРАЗИТЬ(... КАК Число(m, n)).
- ВЫРАЗИТЬ на операнды - когда на какой-то СУБД точности не хватает; ВЫРАЗИТЬ на результат - когда точности хватает
  везде, но она разная. Можно и то и другое.
- Разрядность задавать минимально достаточную: завышение снижает точность последующих вычислений и скорость.
  Самый жесткий предел среди СУБД - 31 разряд суммарно (целая + дробная часть).

```bsl
// ВЫРАЗИТЬ(ВЫРАЗИТЬ(Т.Цена * Т.Количество КАК Число(25, 10))
//          / ВЫРАЗИТЬ(Т.Делитель КАК Число(15, 10)) КАК Число(30, 10)) КАК Доля
```

### std726 Оператор ПОДОБНО - [its](https://its.1c.ru/db/v8std/content/726/hdoc)
Стандарт
- Правый операнд ПОДОБНО - только строковый литерал или параметр (&Шаблон). Нельзя: конкатенация в тексте
  ("123" + "%", &Шаблон + "%"), поле таблицы как шаблон.
- Использовать только переносимые спецсимволы: % (любая последовательность) и _ (один символ). [...] и [^...]
  запрещены (не работают на IBM DB2).
- Длина шаблона - не более 1024 символов (ограничение MS SQL 2005).
- Пользовательский текст экранировать: спецсимволы _ % [ ] ^ и сам символ экранирования (задваивается) префиксовать
  символом (например, ~) и добавлять СПЕЦСИМВОЛ "~". Иначе ввод со скобками даст ошибку СУБД (PostgreSQL: invalid
  regular expression). УстановитьПараметр сам ничего не экранирует.
- В БСП - ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе; без БСП - своя функция с теми же заменами
  (сначала ~ -> ~~, затем %, _, [, ], ^).
- Сравнение ПОДОБНО регистронезависимое.

```bsl
// ГДЕ Номенклатура.Наименование ПОДОБНО &Шаблон СПЕЦСИМВОЛ "~"
Запрос.УстановитьПараметр("Шаблон",
	"%" + ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе(СтрокаПоиска) + "%");
```

### std758 Псевдонимы источников данных - [its](https://its.1c.ru/db/v8std/content/758/hdoc)
Стандарт
- Псевдоним источника - осмысленный, из терминов предметной области, отражает роль таблицы в данном запросе
  (ОстаткиНаСкладах, а не Таблица2).
- Правила как для имен переменных: слова слитно, каждое с прописной (включая однобуквенные предлоги); не начинать
  с "_"; не из одного символа.
- Не использовать имена классов метаданных ("Справочник", "Документ") как псевдоним.
- Универсальный псевдоним (Таблица) допустим в универсальных механизмах, где источник подставляется в текст при
  выполнении.

### std787 Вычисление количества записей - [its](https://its.1c.ru/db/v8std/content/787/hdoc)
Стандарт
- Считать строки только через КОЛИЧЕСТВО(*) или КОЛИЧЕСТВО(Поле), не СУММА(1): по умолчанию число в СУБД имеет
  7 разрядов, на 10 млн+ записей будет переполнение.
- Если нужен условный счет и КОЛИЧЕСТВО неприменимо - расширять разрядность: СУММА(ВЫБОР КОГДА ... ТОГДА
  ВЫРАЗИТЬ(1 КАК ЧИСЛО(17, 0)) ИНАЧЕ 0 КОНЕЦ).

## Оптимизация запросов

### std652 Несоответствие индексов и условий запроса - [its](https://its.1c.ru/db/v8std/content/652/hdoc)
Методическая рекомендация
- Для каждого условия (ГДЕ, СОЕДИНЕНИЕ ... ПО, параметры виртуальной таблицы, ИМЕЮЩИЕ) должен быть подходящий
  индекс: содержит все поля условия, они стоят в начале индекса и идут подряд без "вклинившихся" полей. Иначе СУБД
  сканирует таблицу/индекс - медленно и больше блокировок.
- Порядок условий в тексте запроса не важен, важен порядок полей в индексе.
- Платформа создает сама: индекс по ссылке для объектных таблиц; по регистратору для движений подчиненных регистров;
  по периоду + всем измерениям (в порядке конфигуратора) для итогов регистров накопления; по периоду + счету + всем
  измерениям для итогов регистров бухгалтерии.
- Если не хватает - индексировать реквизит; у справочников и документов - с режимом "Индексировать с доп.
  упорядочиванием" (работает для отбора в списке, отсортированном по основному представлению).
- Индексы только под известный запрос, не "на всякий случай": замедляют запись. Не индексировать первое измерение
  регистра (покрыто основным индексом) и низкоселективные поля (Булево - только если нужное значение редкое и
  ищется всегда именно оно).
- Отбор по неначальному измерению -> индексировать это измерение или переставить измерение выше (осторожно: могут
  замедлиться другие запросы).

### std654 Разыменование ссылочных полей составного типа - [its](https://its.1c.ru/db/v8std/content/654/hdoc)
Стандарт
- Обращение "через точку" (Поле.Реквизит) = неявное соединение с таблицей ссылки, плюс таблицы ее RLS.
- От поля составного типа (Регистратор, любая ссылка) "через точку" - соединение со ВСЕМИ возможными таблицами и их
  RLS. Это крайне нежелательно; каждое исключение анализировать.
- Составной тип описывать ровно нужными типами; без необходимости не ставить "любая ссылка", "ссылка на любой
  документ".
- Денормализовать ради скорости: хранить нужное значение в самой таблице (например, реквизит ДатаРегистратора в
  регистре, заполняемый при проведении).
- В запросе ограничивать типы через ВЫРАЗИТЬ(Поле КАК Документ.Х).Реквизит + ССЫЛКА в условии; в универсальном
  запросе подставлять тип в ВЫРАЗИТЬ динамически.

```bsl
// ВЫБОР КОГДА Продажи.Регистратор ССЫЛКА Документ.РеализацияТоваров
//      ТОГДА ВЫРАЗИТЬ(Продажи.Регистратор КАК Документ.РеализацияТоваров).Дата
// КОНЕЦ КАК ДатаДокумента
// ...
// ГДЕ Продажи.Регистратор ССЫЛКА Документ.РеализацияТоваров
```

### std655 Соединения с вложенными запросами и виртуальными таблицами - [its](https://its.1c.ru/db/v8std/content/655/hdoc)
Стандарт
- Не соединять с вложенными запросами (с любой стороны соединения). Соединять только таблицы метаданных и временные
  таблицы: вложенный запрос выносить в ПОМЕСТИТЬ (с ИНДЕКСИРОВАТЬ ПО при необходимости) в пакете. Исключение -
  вложенный запрос сканирует мало записей. Почему: оптимизатор не знает размер подзапроса и выбирает плохой план -
  замедление на порядки, нестабильность, зависимость от статистик и СУБД.
- Если соединение с виртуальной таблицей (например, .Остатки) работает медленно - вынести ее во временную таблицу.
- Не писать вложенные соединения (СОЕДИНЕНИЕ внутри СОЕДИНЕНИЕ с общим ПО) - это неявный подзапрос. Писать
  последовательные соединения. Внимание: результат может отличаться; если вложенность осмысленна - заменить на
  последовательное (лучше) или на временную таблицу.

```bsl
// ВЫБРАТЬ ... ПОМЕСТИТЬ ВТЛимиты ИЗ РегистрСведений.Лимиты ... ИНДЕКСИРОВАТЬ ПО Контрагент
// ;
// ВЫБРАТЬ ... ИЗ Документ.Реализация КАК Реализация
//   ЛЕВОЕ СОЕДИНЕНИЕ ВТЛимиты КАК Лимиты ПО Лимиты.Контрагент = Реализация.Контрагент
```

### std656 Вложенные запросы в условии соединения - [its](https://its.1c.ru/db/v8std/content/656/hdoc)
Стандарт
- Не использовать вложенный запрос внутри условия ПО (например, Цены.Период В (ВЫБРАТЬ МАКСИМУМ ...)): сильное
  замедление, на некоторых СУБД - неработоспособность.
- Переписать пакетом: сначала во временную таблицу ключ + МАКСИМУМ(Период), затем соединение по равенству периода.

### std657 Обращения к виртуальным таблицам - [its](https://its.1c.ru/db/v8std/content/657/hdoc)
Стандарт
- Все условия по виртуальной таблице передавать в ее параметры (Остатки(, Склад = &Склад)), а не в ГДЕ внешнего
  запроса - иначе СУБД может сначала построить всю таблицу, а потом фильтровать.
- В параметрах - простые условия вида Измерение = Значение. Не использовать подзапросы и соединения, включая
  неявные: "через точку" и добавляемые RLS.
- Если подзапрос в параметре неизбежен: в нем одна таблица без соединений; для табличной части - без обращения к
  реквизитам шапки; для таблицы с ТЧ - без обращения к ТЧ; временная таблица - без ГДЕ; постоянная таблица - ГДЕ
  только если оно истинно для 80%+ записей, и ее RLS только простой (Реквизит = Значение, ГДЕ Истина). Стандартные
  шаблоны RLS БСП (Управление доступом) добавляют ЕСТЬ с соединениями - тогда переписать через временную таблицу или
  привилегированный режим.
- Из нескольких условий-подзапросов в параметре оставить одно, самое фильтрующее; остальные - во внешний запрос.
  Несколько В по одной временной таблице заменять на (Поле1, Поле2, Поле3) В (ВЫБРАТЬ ... ИЗ ВТ).

### std658 Эффективные условия запросов - [its](https://its.1c.ru/db/v8std/content/658/hdoc)
Стандарт
- Основное условие (самое ограничивающее, части соединены через И) в ГДЕ/ПО/параметрах виртуальной таблицы должно
  идти по индексированным полям. Дополнительные условия добавляются к нему через И и могут быть любыми.
- Операции основного условия: для всех полей индекса кроме последнего - только = и И; для последнего (или
  единственного) - =, >, <, >=, <=, ПОДОБНО, МЕЖДУ, В, ИЛИ (сводимое к В). Нельзя: арифметика, функции, НЕ,
  неравенство <>.
- Где индекс: для ГДЕ/виртуальной таблицы - в основной таблице выборки; для ПО ЛЕВОГО соединения - в правой
  таблице; для ПО ВНУТРЕННЕГО - в большей таблице. Предпочитать индексы, которые платформа создает сама. Разные
  индексированные реквизиты = разные индексы, используется только один.
- Можно не соблюдать, если таблица всегда < 1000 записей или запрос очень редкий.
- Если соблюсти нельзя: преобразовать условие; добавить вычисляемое при записи индексированное поле; пересмотреть
  архитектуру.
- ИЛИ в основном условии - только по одному полю (сводится к В). ИЛИ по разным полям -> ОБЪЕДИНИТЬ ВСЕ двух выборок
  (оба поля индексированы; проверить эквивалентность результата). В дополнительном условии ИЛИ без ограничений.
- ПОДСТРОКА(Поле, 1, N) = "..." -> Поле ПОДОБНО "...%". Шаблон не должен начинаться с % или _ - для поиска с
  середины завести вычисляемое индексированное поле.
- Функции дат (МЕСЯЦ(Поле) = 1) -> Поле МЕЖДУ &Начало И &Конец.
- ВЫБОР и арифметика над полями - только в дополнительных условиях.
- Не назначать пользователю несколько ролей с разными RLS на одно право одного объекта: условия склеиваются через
  ИЛИ и запрос деградирует (медленно, лишние блокировки). Один объект - одна роль на право, либо одинаковые RLS во
  всех ролях.

```bsl
// ГДЕ Таблица.Дата МЕЖДУ &НачалоМесяца И &КонецМесяца   // основное, по индексу
//   И (Таблица.Статус = &С1 ИЛИ Таблица.Сумма - Таблица.Оплачено > 0) // дополнительное
```

### std708 Разрешение итогов для периодических регистров сведений - [its](https://its.1c.ru/db/v8std/content/708/hdoc)
Методическая рекомендация
- Включать "Разрешить итоги: срез последних/первых" только при ВСЕХ условиях: в регистре много данных (цены - да,
  курсы валют - нет); есть частые запросы к СрезПоследних/СрезПервых без указания периода; прочие условия
  виртуальной таблицы только по измерениям (и разделителям в режиме "Независимо и совместно"); RLS регистра тоже
  только по ним.
- Подумать о переделке запросов под эти условия (например, если нет записей будущими датами - запрашивать срез без
  даты).
- В остальных случаях не включать: срез почти всегда на конкретную дату (дата документа) или в условиях подзапросы
  и "через точку" (Валюта.Код = ...).
- Свой механизм пересчета итогов не нужен: обновляются при каждой записи набора. Исключение - если запись итогов
  отключали через РегистрСведенийМенеджер.УстановитьИспользованиеИтогов(Ложь).

### std729 Общие требования по разработке оптимальных запросов - [its](https://its.1c.ru/db/v8std/content/729/hdoc)
Методическая рекомендация
- Выбирать ровно нужные поля и строки; не ВЫБРАТЬ *. Свертку, сортировку, вычисления по возможности делать в СУБД,
  а не на сервере 1С.
- Минимизировать число обращений к СУБД (см. std436).
- Но не усложнять запрос любой ценой: лучше несколько простых частных текстов под разные условия, чем один
  универсальный; иногда эффективнее досчитать на сервере 1С.
- Не добавлять вложенные запросы "для читаемости"; избегать сложных условий ПО/ГДЕ с подзапросами и ВЫБОР;
  минимум таблиц - уже 5-7 таблиц в запросе может быть много (особенно DB2, PostgreSQL, Oracle).
- Проверять план (консоль запросов, техжурнал, средства СУБД); timeout warning в плане - признак слишком сложного
  запроса.

### std733 Эффективное обращение к виртуальной таблице «Остатки» - [its](https://its.1c.ru/db/v8std/content/733/hdoc)
Стандарт; регистры накопления и бухгалтерии
- Самый быстрый вариант (чтение таблицы текущих итогов без группировки) получается, когда: остатки берутся без даты;
  разделение итогов не используется (оно, правда, повышает параллельность записи); внешний запрос использует все
  измерения (в ВЫБРАТЬ или в ПО).
- Для текущих остатков не передавать дату (СегодняшняяДата) в параметр - иначе читаются и движения.
- Измерение, отфильтрованное в параметре, повторить в условии ПО внешнего запроса.

```bsl
// ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ОстаткиТоваров.Остатки(, Склад = &Склад) КАК Остатки
//   ПО Остатки.Номенклатура = Товары.Ссылка И Остатки.Склад = &Склад
```

### std777 Использование временных таблиц - [its](https://its.1c.ru/db/v8std/content/777/hdoc)
Стандарт
- Временные таблицы - прежде всего для производительности и стабильности; для "красоты кода" - понимая, что может
  стать медленнее.
- Не создавать ВТ на сотни тысяч записей (медленная запись, место на диске) - обрабатывать порциями.
- Помещать только нужные последующим запросам строки и поля.
- Не создавать/удалять ВТ в цикле, если можно создать одну до цикла. Не копировать ВТ ради переименования -
  передавать имя таблицы.
- Индексировать (ИНДЕКСИРОВАТЬ ПО), когда это ускоряет: большая ВТ в соединении - поля из ПО; ВТ в подзапросе
  В (...) - поля, соответствующие левой части В. Маленькие (< 1000 записей) не индексировать. Если условий несколько,
  а часто проверяется одно - индекс под него.

### std791 Дополнительные индексы - [its](https://its.1c.ru/db/v8std/content/791/hdoc)
Стандарт
- Дополнительный индекс - индекс по нескольким полям объекта метаданных, с возможностью включаемых (неключевых)
  полей. Применять в функциональности для крупных предприятий с КОРП-лицензией; если решение работает только на ПРОФ
  - нельзя.
- С выключенными доп. индексами производительность должна быть приемлемой примерно до 100 000 - 1 000 000 записей;
  выше - гарантируется включением доп. индексов. Тестировать в обоих режимах.
- Если приемлемая скорость достижима без них - обычные индексы.
- Держать одну ветку кода, без альтернативной реализации "без доп. индексов". Исключение - если без них на малом
  объеме не достигается минимум: интерактив (открытие списка) до 1 с, отчеты медленнее не более чем в 2 раза.
- Поле, нужное только чтобы не читать таблицу (не в условиях), делать включаемым, а не ключевым.
