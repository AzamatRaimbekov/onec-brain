## Обработка и модификация данных

### std460 Использование управляемого режима блокировки - [its](https://its.1c.ru/db/v8std/content/460/hdoc)
Стандарт; управляемое и обычное приложение
- Свойство конфигурации "Режим управления блокировкой данных" = Управляемый.
- В этом режиме чтение блокируется другой транзакцией только при несовместимых управляемых блокировках.
- Явную управляемую блокировку (БлокировкаДанных) ставить ДО чтения, если прочитанное будет изменяться или должно
  оставаться неизменным до конца транзакции.
- Блокировать только те записи, которые реально обрабатываются кодом.
- ДЛЯ ИЗМЕНЕНИЯ в запросах не писать - в управляемом режиме оно бессмысленно.
- Почему: автоматический режим держит высокую изоляцию на уровне СУБД и дает избыточные блокировки (СУБД не знает
  структуры объектов 1С).

### std490 Блокировка данных объекта для редактирования из кода - [its](https://its.1c.ru/db/v8std/content/490/hdoc)
Стандарт; управляемое и обычное приложение
- Перед изменением существующего объекта из кода ставить объектную (пессимистическую) блокировку:
  Объект.Заблокировать() или ЗаблокироватьДанныеДляРедактирования(Ссылка). Это проверяет, не редактирует ли объект
  кто-то еще, и мешает параллельной правке; иначе пользователь потом не сможет записать свои изменения.
- Объектная блокировка не запрещает запись другим сеансам, а лишь не дает двум сторонам одновременно ее взять; это
  не транзакционная блокировка.
- Интерактивный сценарий: при неудаче показать пользователю ошибку блокировки (исключение платформы с данными о
  компьютере, пользователе, сеансе).
- Фоновый/регламентный сценарий: Попытка вокруг Заблокировать(); при неудаче пропустить объект, записать
  Предупреждение в журнал регистрации и повторить при следующем запуске.
- Форма сама блокирует объект основного реквизита при редактировании.
- Не проверять блокировку: в операциях с приоритетом выше интерактива (загрузка при обмене); в гарантированно
  монопольных действиях (обновление и начальное заполнение ИБ).

```bsl
ОбъектФайла = Ссылка.ПолучитьОбъект();
Попытка
	ОбъектФайла.Заблокировать();
Исключение
	ЗаписьЖурналаРегистрации(НСтр("ru = 'Обновление файлов'"), УровеньЖурналаРегистрации.Предупреждение,
		, ОбъектФайла, ОбработкаОшибок.ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	Возврат; // попробуем в следующий раз
КонецПопытки;
ОбъектФайла.ПолноеНаименование = НовоеНаименование;
ОбъектФайла.Записать();
```

### std496 Чтение отдельных реквизитов объекта из базы данных - [its](https://its.1c.ru/db/v8std/content/496/hdoc)
Стандарт
- Ссылка.ПолучитьОбъект() и обращение Ссылка.Реквизит "через точку" в коде загружают весь объект с табличными
  частями.
- Для чтения отдельных реквизитов использовать запрос или функции БСП ОбщегоНазначения.ЗначенияРеквизитовОбъекта /
  ЗначениеРеквизитаОбъекта.

```bsl
Реквизиты = ОбщегоНазначения.ЗначенияРеквизитовОбъекта(СтранаСсылка, "Код, Наименование");
КодСтраны = Реквизиты.Код;
```

### std497 Запись событий в историю работы пользователя - [its](https://its.1c.ru/db/v8std/content/497/hdoc)
Стандарт (формулировки "рекомендуется"); только управляемое приложение
- Интерактивное добавление/изменение объектов попадает в историю работы автоматически.
- Прочие действия пользователя, которые записывают объекты (например, команда "Поместить файл"), добавлять явно:
  ИсторияРаботыПользователя.Добавить(ПолучитьНавигационнуюСсылку(Ссылка)) (тип МенеджерИсторииРаботыПользователя).

### std648 Ответственное чтение данных - [its](https://its.1c.ru/db/v8std/content/648/hdoc)
Стандарт; п.1.1 и п.2 - управляемое и обычное приложение
- Ответственное чтение - любое чтение, по результату которого меняются данные ИБ или принимаются решения.
- Его выполнять в транзакции с управляемой блокировкой, установленной ДО чтения. Примеры: чтение при проведении для
  движений; выгрузка, которая должна быть целостной (клиент-банк); групповая обработка и реструктуризация в
  обработчиках обновления (перед изменением ссылочных объектов обычно еще и объектная блокировка).
- Не требуется: динамические списки, поиск, большинство отчетов; условно-постоянные данные (константа
  ВалютаРегламентированногоУчета, учетная политика); монопольные операции (обновление, начальное заполнение); данные
  одного пользователя (персональные); мобильное приложение.
- В обработчиках ПередЗаписью, ПриЗаписи, ПередУдалением (и их подписках) уже идет системная транзакция - свою
  открывать не нужно, достаточно блокировки.
- Чтение с последующим изменением тех же данных - Исключительная блокировка до чтения (иначе взаимоблокировка).
- Чтение без изменения (например, для движений) - Разделяемая на читаемое + Исключительная на изменяемое.
- После ПолучитьОбъект() под блокировкой проверять на Неопределено - объект могли удалить.

```bsl
НачатьТранзакцию();
Попытка
	Блокировка = Новый БлокировкаДанных;
	Элемент = Блокировка.Добавить("РегистрСведений.СчетчикиЗаметок");
	Элемент.УстановитьЗначение("Предмет", Предмет);
	Элемент.Режим = РежимБлокировкиДанных.Исключительный;
	Блокировка.Заблокировать();
	// прочитать текущее значение запросом, увеличить, записать набор
	ЗафиксироватьТранзакцию();
Исключение
	ОтменитьТранзакцию();
	ЗаписьЖурналаРегистрации(НСтр("ru = 'Заметки'"), УровеньЖурналаРегистрации.Ошибка,,,
		ОбработкаОшибок.ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	ВызватьИсключение;
КонецПопытки;
```

### std783 Транзакции: правила использования - [its](https://its.1c.ru/db/v8std/content/783/hdoc)
Стандарт
Особенности платформы: вложенных транзакций нет; после исключения транзакцию в общем случае нельзя зафиксировать,
даже если исключение перехвачено; любая запись в БД неявно открывает транзакцию. Нарушения дают ошибку
"В этой транзакции уже происходили ошибки".
- НачатьТранзакцию и ЗафиксироватьТранзакцию/ОтменитьТранзакцию - строго парные и в одном методе.
- НачатьТранзакцию - вне Попытки, непосредственно перед Попытка.
- Все действия после НачатьТранзакцию (чтение, блокировка, запись) - внутри одной Попытки.
- ЗафиксироватьТранзакцию - последний оператор Попытки перед Исключение.
- В Исключение первым делом ОтменитьТранзакцию, затем остальное; рекомендуется запись в журнал регистрации; если
  возможна внешняя транзакция - в конце ВызватьИсключение (иначе внешняя не узнает об ошибке и упадет с "В данной
  транзакции происходила ошибка").
- Не открывать транзакцию явно, если делается только запись одного объекта (платформа откроет сама) и не нужно
  ответственное чтение (обычно - запись нового объекта/набора). При ПолучитьОбъект()/Прочитать() решать, нужно ли
  ответственное чтение.
- Метод, который вызывается только внутри уже открытой транзакции (ПередЗаписью, ОбработкаПроведения и т.п.), не
  должен открывать свою.
- Вложенная транзакция оправдана для понятных сообщений об ошибке на своем уровне (например, "Не удалось добавить
  подпись к ... по причине ...").
- В обработчике исключения при еще активной (внешней) транзакции к БД не обращаться, в т.ч. неявно (получение
  представления ссылки) - будет "В этой транзакции уже происходили ошибки".
- В одну транзакцию - только неделимые по бизнес-логике действия (документ + его движения). Независимые действия не
  объединять; исключение - пакетная обработка несвязанных объектов ради скорости, с разумным размером порции.
- Транзакция не дольше 20 секунд в нагруженной системе (таймаут ожидания блокировки по умолчанию - 20 с, потом
  "Превышено время ожидания установки блокировки"). Большие загрузки (например, адресный классификатор ~1 Гб) делить
  на порции и реализовать откат к предыдущей версии самостоятельно.
- Длинная транзакция держит журнал транзакций СУБД, блокировки, память сервера 1С. При таймаутах блокировок:
  выносить действия из транзакции, оптимизировать алгоритм, проверять избыточность блокировок.
- Внутри транзакции минимум: тяжелые расчеты - до нее; контроль остатков - простым запросом после записи;
  проверка заполнения - вне транзакции; запросы без блокировки - до начала; запросы в транзакции оптимизировать.
- Запрещено в транзакции обращаться к внешним ресурсам (сетевые папки, сайты, почта, FTP, HTTP, веб-сервисы): долго,
  недоступность, таймауты.
- Отключение итогов (УстановитьИспользованиеИтогов(Ложь)) + запись + включение - обязательно в одной транзакции,
  иначе другие сеансы получат ошибку при чтении среза последних. ПересчитатьИтоги - после фиксации.

```bsl
НачатьТранзакцию();
Попытка
	Блокировка = Новый БлокировкаДанных;
	Элемент = Блокировка.Добавить("Документ.ПриходнаяНакладная");
	Элемент.УстановитьЗначение("Ссылка", Ссылка);
	Блокировка.Заблокировать();
	// чтение и запись данных
	ЗафиксироватьТранзакцию();
Исключение
	ОтменитьТранзакцию();
	ЗаписьЖурналаРегистрации(НСтр("ru = 'Выполнение операции'"), УровеньЖурналаРегистрации.Ошибка,,,
		ОбработкаОшибок.ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	ВызватьИсключение;
КонецПопытки;
```

### std792 Многократная запись регистров сведений и накопления - [its](https://its.1c.ru/db/v8std/content/792/hdoc)
Стандарт (формулировки "не рекомендуется/рекомендуется")
- Не записывать наборы регистров сведений/накопления в цикле по одной-нескольким записям - в разы медленнее.
  Ориентир - порции по 1000 записей в одном наборе.
- Если в большом наборе меняется не более 30% записей - не перезаписывать весь набор (удаление всех + вставка всех,
  раздувание журнала транзакций), а записывать только изменения.
- Пустой регистр, только добавление - Записать(Ложь). Иначе режимы замещения: РежимЗамещения.Слияние,
  РежимЗамещения.Удаление (с 8.3.26), РежимЗамещения.Обновление (с 8.3.27) - пакетно, порциями.
- Известные удаления по ключам -> один набор с этими ключами и Записать(РежимЗамещения.Удаление), а не набор на
  каждую запись.
- Обработчик обновления: блокировку ставить по источнику данных (ИсточникДанных + ИспользоватьИзИсточникаДанных),
  изменения вычислять одним запросом, писать одним набором в режиме Обновление.
- Частичное обновление независимого регистра сведений: запросом сравнить новые и существующие записи без загрузки в
  сервер 1С; лишние -> Удаление, недостающие и измененные -> Слияние; если оба результата пустые - ничего не
  блокировать и не писать.
- Регистры, подчиненные регистратору: ключ строки - Регистратор + НомерСтроки, Слияние недоступно, при Удаление
  НомерСтроки оставшихся пересчитывается. Поэтому НомерСтроки - лишь счетчик, порядок не важен, из сравнения его
  исключать. Алгоритм (наборы с РасширенныеРежимыЗамещения = Истина и сброшенным отбором): сначала Обновление -
  новые записи на номера строк удаляемых (не больше их числа); оставшиеся лишние - Удаление по ключам; иначе
  оставшиеся новые - Добавление без НомерСтроки (с 8.3.26).
- Оптимизировать запись движений так стоит, когда проведение медленное (ТЧ на тысячи строк, изменения малы);
  не применять при обновлении сразу по многим регистраторам (закрытие месяца, восстановление последовательности).

```bsl
Набор = РегистрыСведений.НастройкиПользователей.СоздатьНаборЗаписей();
Для Каждого Настройка Из УдаляемыеНастройки Цикл
	Запись = Набор.Добавить();
	Запись.Пользователь = Пользователь;
	Запись.Команда = Настройка.Команда;
КонецЦикла;
Набор.Записать(РежимЗамещения.Удаление); // одна запись в БД вместо цикла наборов
```

## Избыточные блокировки и методы оптимизации

### std659 Общие сведения об избыточных блокировках - [its](https://its.1c.ru/db/v8std/content/659/hdoc)
Методическая рекомендация
- Ожидание возникает, только когда два сеанса захватывают один и тот же неделимый ресурс; параллельность зависит от
  того, насколько мелко "нарезаны" данные.
- Ошибки проектирования структуры метаданных ведут к массовым избыточным блокировкам. Проверять в первую очередь
  последовательности, регистры бухгалтерии и регистры накопления.
- Связанные причины: блокирующее чтение остатков в начале транзакции (std661), автоматический режим блокировок
  (std460), неподходящие индексы (std652), "через точку" от составных полей (std654), соединения с подзапросами
  (std655, std656), фильтр виртуальных таблиц в ГДЕ (std657), ИЛИ в условиях (std658).

### std661 Блокирующее чтение остатков в начале транзакции - [its](https://its.1c.ru/db/v8std/content/661/hdoc)
Стандарт
- Контроль остатков требует блокирующего чтения (иначе два пользователя спишут один остаток и уйдут в минус), но
  блокировку держать как можно меньше по времени - ставить ее в конце транзакции.
- Сначала решить, где контроль вообще нужен: не нужен для приходных документов и при перепроведении, если списание
  не выросло.
- Порядок в ОбработкаПроведения: (1) явно записать движения регистров без контроля, всегда в одинаковом порядке
  (например, по алфавиту); у этих регистров накопления/бухгалтерии включено разделение итогов, у наборов
  БлокироватьДляИзменения = Ложь; (2) выполнить прочие действия; (3) в самом конце записать регистры с контролем,
  у их наборов БлокироватьДляИзменения = Истина (против взаимоблокировок - остатки блокируются по измерениям набора);
  (4) запросом прочитать только ОТРИЦАТЕЛЬНЫЕ остатки по этим измерениям; есть - отказ, нет - фиксация. Явная
  блокировка для этого запроса не нужна - данные уже заблокированы записью.
- Запрос остатков в ПередЗаписью набора (в начале транзакции) блокирует итоги для всех и сводит на нет разделение
  итогов - переносить проверку в ОбработкаПроведения/ПриПроведении после записи всех движений.

```bsl
Движения.ДенежныеСредства.Записать();            // без контроля, по алфавиту
Движения.ТоварыНаСкладах.БлокироватьДляИзменения = Истина;
Движения.ТоварыНаСкладах.Записать();             // последним - с контролем
// запрос: ...Остатки(, (Склад, Номенклатура) В (&Ключи)) ГДЕ КоличествоОстаток < 0
// не пусто -> Отказ = Истина
```

### std662 Сдвиг границы последовательности документов - [its](https://its.1c.ru/db/v8std/content/662/hdoc)
Стандарт (формулировки "не рекомендуется/рекомендуется")
- Не двигать границу последовательности при проведении: граница по одному набору измерений - один ресурс, все
  проводящие документы по нему (например, по одной организации) выстраиваются в очередь.
- Перенести сдвиг границы в регламентную обработку с заданной частотой (например, расчет себестоимости не в
  оперативном режиме, а регламентно).

### std663 Режим разделения итогов для регистров бухгалтерии - [its](https://its.1c.ru/db/v8std/content/663/hdoc)
Стандарт (формулировки "рекомендуется"); управляемое и обычное приложение
- При оперативной многопользовательской записи в регистр бухгалтерии включать разделение итогов: тогда запись
  параллельна даже при совпадении периода, счета и всех измерений. Без него таблица остатков - узкое место.
- Разделение надо разрешить в конфигураторе и включить в режиме 1С:Предприятие.
- При контроле остатков по этому регистру эффекта не будет - контроль переносить в конец транзакции (std661).

### std664 Режим разделения итогов для регистров накопления - [its](https://its.1c.ru/db/v8std/content/664/hdoc)
Стандарт (формулировки "не рекомендуется/рекомендуется")
- Остатки по одной комбинации измерений - один ресурс; параллельность определяется составом измерений. Подбирать
  измерения под нужную "нарезку" остатков.
- Блокировка возникает, только если наборы двух сеансов содержат строку с совпадающими значениями ВСЕХ измерений.
- Если состава измерений мало для нужной параллельности - включать разделение итогов (как у регистров бухгалтерии).
- Разделение итогов не помогает при контроле остатков - переносить контроль ближе к концу транзакции.
