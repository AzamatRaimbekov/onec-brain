# Организация хранения данных - стандарты 1С (v8std)

> Пересказ раздела «Организация хранения данных» системы стандартов its.1c.ru/db/v8std, снят 2026-10-07. Это не
> копия: при сомнении открыть первоисточник по ссылке. Нумерация stdNNN совпадает с сайтом.

Содержание:
- std683 Общие сведения об организации хранения данных (выбор типа объекта метаданных)

- std474 Имя, синоним, комментарий
- std432 Использование реквизитов строкового типа
- std473 Использование кодов (номеров) объектов конфигурации

Область применения всех документов раздела - управляемое, мобильное и обычное приложение, если не указано иное.

## Выбор типа объекта метаданных

### std683 Общие сведения об организации хранения данных - [its](https://its.1c.ru/db/v8std/content/683/hdoc)
Рекомендация
- Сначала отнести сущность к одному из трех блоков, потом выбрать вид объекта внутри блока. Отчеты и обработки
  данных не хранят, а опираются на все блоки.
- Блоки:
  1. **НСИ (условно-постоянная информация)** - редко меняется, не привязана ко времени, многократно используется;
     нужна иерархия/группировка, код и наименование, серии кодов.
  2. **События процессов** - привязаны ко времени, требуют документального подтверждения и последовательности на
     оси времени; нужны дата, номер, состояние (проведен/отменен, старт/финиш процесса), сквозная нумерация разных
     видов или в пределах периода.
  3. **Накопленные сведения / показатели** - необъектные данные (остатки, история продаж, курсы); ни иерархии, ни
     кода, ни нумерации, ни отслеживания состояний не требуется.
- Внутри блока НСИ:
  - двойная запись -> План счетов; начисления/удержания -> План видов расчета; перечень свойств, состав и типы
    которых задает пользователь -> План видов характеристик (эти три - только управляемое/обычное приложение);
  - одиночное значение, правится администратором, ссылки на него не нужны -> Константа;
  - фиксированный список без реквизитов, пользователь не редактирует -> Перечисление;
  - остальное -> Справочник (иерархия, в т.ч. между разными сущностями через подчинение; ввод на основании;
    нумерация в пределах группы или владельца).
- Внутри блока событий (Задача и Бизнес-процесс - только управляемое/обычное приложение):
  - одиночное событие для исполнителя (пользователь, роль, группа) без движений -> Задача (состояния «новый»,
    «выполнено»);
  - регулярный процесс из цепочки действий, возможна вложенность процессов -> Бизнес-процесс + Задачи;
  - остальное, особенно если нужны вторичные данные, журналы, состояния «проведен/не проведен» -> Документ.
- Внутри блока показателей:
  - двойная запись -> Регистр бухгалтерии; результаты расчета начислений -> Регистр расчета (оба - управл./обычное);
  - приход/расход, остатки и обороты, обязательная связь с регистратором -> Регистр накопления;
  - всё прочее (наборы сведений, срез на дату, связь с документом не обязательна) -> Регистр сведений.
- Пример: анкета с датой, порождающая ответы как статистику, - событие с вторичными данными, значит Документ.

### std541 Уточнение сущности объекта метаданных - [its](https://its.1c.ru/db/v8std/content/541/hdoc)
Стандарт
- Разные по смыслу сущности - разные объекты метаданных (Организации и Подразделения - отдельные справочники).
- Если вид/состояние объекта уточняется внутри одного объекта, заводить явный реквизит-признак (Булево или
  перечисление вида). Не выводить вид по косвенным признакам, например по заполненности другого реквизита.
  - Плохо: «обособленное подразделение» = заполнена ГоловнаяОрганизация. Хорошо: отдельный булев
    ОбособленноеПодразделение, от него зависит обязательность ГоловнаяОрганизация.
- Для сущностей с несколькими состояниями - один реквизит-перечисление статусов (работает/уволен, расширяемый), а не
  набор булевых флагов, дублирующих даты.

## Именование и свойства реквизитов

### std474 Имя, синоним, комментарий - [its](https://its.1c.ru/db/v8std/content/474/hdoc)
Стандарт
- Синоним заполнять обязательно у всех объектов и подчиненных (реквизиты, ТЧ, их реквизиты, измерения, ресурсы):
  осмысленно и кратко, одинаково идентифицирует сущность во всем интерфейсе. Не «Что», а «Предмет контроля».
- Без сокращений в синонимах, кроме общепринятых для аудитории («Сумма (регл.)», НДС, МСФО).
- Только общепринятые термины: без сленга, искаженных названий продуктов/компаний, транслита в обе стороны. Нет
  устоявшегося перевода - писать оригинал («Microsoft Excel», не «Эксель»/«MS Excel»).
- Синонимы стандартных реквизитов и стандартных ТЧ задавать по прикладному смыслу. Для Родитель и Владелец синоним
  по умолчанию оставлять нельзя никогда («Папка», а не «Владелец»); Наименование - по смыслу («Имя файла», «ФИО»).
- Объекты/реквизиты со схожим назначением: синоним каждого должен полностью его описывать («Банковские счета
  организаций» и «... контрагентов»; «Количество (в наличии)» и «Количество (по учету)»; не «Наименование» и
  «Полное наименование», а «Рабочее наименование» и «Наименование для печати»).
- Имя строить из синонима: убрать пробелы и недопустимые символы, слова с заглавной. Допустимо опускать в имени
  последние малозначащие слова, союзы и предлоги, а в синониме - технические хвосты имени.
- Исключения: объекты с префиксом Удалить; не переименовывать объекты под обратной совместимостью (особенно в
  библиотеках - в пределах редакции).
- Имя объекта метаданных - не длиннее 80 символов.
- Подчиненный объект не называть так же, как владелец (измерение не Пользователь в регистре ИсполнителиЗадач, а
  Исполнитель).
- Не использовать имена таблиц языка запросов (Документ, Справочник, РегистрСведений, Сведения в РегистрСведений...):
  ломают запросы и конструктор.
- Комментарий - только если нужно пояснение разработчику; с прописной буквы, точки только после сокращений.
- Буква «ё» в именах, синонимах, комментариях запрещена.

### std432 Использование реквизитов строкового типа - [its](https://its.1c.ru/db/v8std/content/432/hdoc)
Стандарт
- Строковые реквизиты: Допустимая длина = Переменная с заданной максимальной длиной. Фиксированная - только если
  алгоритмам реально нужна гарантированная длина с добивкой пробелами.
- Регламентированная длина - указывать именно ее (ИНН физлица = 12). Строка-конкатенация - сумма длин частей.
- Нерегламентированная - длина «с запасом для большинства случаев»: полное наименование контрагента 250, имя файла
  260, ФИО 100.
- Неограниченная длина допустима только для: (а) объемного пользовательского текста, обычно многострочного
  (комментарий, описание); (б) машинных технических данных (XML, заголовки писем).
- В запросах неограниченную строку при сравнении, группировке, РАЗЛИЧНЫЕ приводить к нужной длине; в остальных
  случаях обрезать не нужно. В СКД вместо этого задавать «Тип значения» поля в наборе данных. Частое приведение -
  сигнал сменить тип на ограниченный.
- В печатных формах строку выводить полностью, без обрезки, независимо от длины реквизита.
```bsl
ВЫБРАТЬ РАЗЛИЧНЫЕ ВЫРАЗИТЬ(Т.Описание КАК СТРОКА(500)) КАК Описание ИЗ Справочник.Заметки КАК Т
```

### std473 Использование кодов (номеров) объектов конфигурации - [its](https://its.1c.ru/db/v8std/content/473/hdoc)
Рекомендация
- Код/номер нужен, если: большие списки (Номенклатура); искать по коду проще, чем по названию (Статьи расходов);
  код несет прикладной смысл (ОКЕИ, номер ГТД).
- Автонумерация не нужна, если код - краткое строковое представление (логин в Пользователи) или приходит извне
  (классификаторы, ГТД).
- Длина кода при автонумерации - от ожидаемого количества объектов: всего, за период (документы, БП) или в пределах
  владельца/родителя; с учетом префиксов (префикс ИБ, организации). Рекомендуемый ряд для типовых: 3, 5, 9, 11.
- С подсистемой БСП «Префиксация объектов» суммарная длина номера/кода с префиксом - не меньше 11 (11, 13, 15...).
- Код-представление - длина по смыслу; внешний код - по источнику. Длину кода рекомендуется делать переменной.
- Если данные вводятся параллельно в нескольких местах (узлы РИБ, другие программы) и потом консолидируются, а код
  строковый с автонумерацией - обязательна автоматическая префиксация (в БСП - подсистема «Префиксация объектов»).

### std728 Ограничения на использование реквизитов составного типа - [its](https://its.1c.ru/db/v8std/content/728/hdoc)
Стандарт
- Составной реквизит, участвующий в соединениях, отборах, упорядочивании, - только из ссылочных типов. Не смешивать
  со Строка, Число, Дата, УникальныйИдентификатор, Булево, ХранилищеЗначения: падает скорость запросов.
- Обход: вместо «ссылка или строка» завести справочник для произвольных значений (ПроизвольныеАдреса), молча
  создавать элемент при записи документа, мусор чистить регламентным заданием.
- Исключение - таблицы заведомо малого объема (до 1000 записей).
- В хранимых объектах не использовать ЛюбаяСсылка, СправочникСсылка, ДокументСсылка и т.п. - перечислять типы явно.
  Исключение - универсальные механизмы, реально работающие с любыми ссылками. Почему: неявные соединения со всеми
  таблицами при обращении через точку, лишние реструктуризации, тяжелое удаление помеченных, неудобный выбор типа.
- (управл./обычное) Массово используемый составной тип - оформлять определяемым типом. Исключение: ведущие измерения
  регистров библиотечных универсальных механизмов - там «широкие» типы допустимы, т.к. сужение определяемого типа
  потребует пересоздать регистр.

### std478 Подсказка и проверка заполнения - [its](https://its.1c.ru/db/v8std/content/478/hdoc)
Стандарт
- (управл./обычное) Подсказку задавать только для реквизитов/измерений/ресурсов, которые видны пользователю и
  требуют пояснения; для ежедневно используемых - не задавать. Не писать в подсказке инструкций - лучше улучшить
  сценарий. Удалять автосгенерированные бессмысленные подсказки групп («Группа шапка»).
- Логически обязательные реквизиты, стандартные реквизиты и ТЧ - «Проверка заполнения» = «Выдавать ошибку»
  (Заказ клиента: Клиент и Товары).
- Все ограничения - по максимуму в метаданных: если хотя бы один сценарий требует заполнения - ставить «Выдавать
  ошибку», а необязательные сценарии исключать в ОбработкаПроверкиЗаполнения (см. std463).
- Обратная схема запрещена: «Не проверять» в свойстве + ручная проверка в коде.
- Условную обязательность показывать в форме условным оформлением: снимать автопометку незаполненного, когда
  проверка не нужна.

### std531 Реквизит «Комментарий» у документов - [its](https://its.1c.ru/db/v8std/content/531/hdoc)
Рекомендация
- У каждого документа - реквизит Комментарий (строка неограниченной длины) для служебных заметок (например, почему
  помечен на удаление). Права на него - как на сам документ.
- Если сценарий предполагает ввод прикладного текста - отдельный реквизит (ДополнительнаяИнформация), а не
  Комментарий.
- Редактор: ВвестиСтроку; в БСП - ОбщегоНазначенияКлиент.ПоказатьФормуРедактированияКомментария.

## Предопределенные, недействительные, константы

### std697 Использование предопределенных элементов - [its](https://its.1c.ru/db/v8std/content/697/hdoc)
Стандарт; платформа 8.3.3+ без режима совместимости 8.2
- Касается справочников, планов счетов, ПВХ, ПВР. По умолчанию создавать предопределенные автоматически:
  ОбновлениеПредопределенныхДанных = Авто, не переключать режим кодом через УстановитьОбновлениеПредопределенныхДанных.
- Во всех ролях держать выключенными права ИнтерактивноеУдалениеПредопределенныхДанных,
  ИнтерактивнаяПометкаУдаленияПредопределенныхДанных, ИнтерактивноеСнятиеПометкиУдаленияПредопределенныхДанных,
  ИнтерактивноеУдалениеПомеченныхПредопределенныхДанных.
- (управл./обычное) Подчиненные узлы РИБ: предопределенные приходят из главного узла. Нужно: загружать сообщение
  обмена до прикладного кода, который их использует; не обращаться к ним в ПриПолученииДанныхОтГлавного и правилах
  регистрации; не обрабатывать их в обработчиках обновления в подчиненном узле. С БСП «Обмен данными» 2.1.4+ первые
  два требования сняты.
- Таблицы с предопределенными вне состава плана обмена РИБ (и на которые не ссылаются таблицы из состава) -
  ставить ОбновлятьАвтоматически, т.к. Авто в подчиненном узле означает «не обновлять». В режиме совместимости 8.3.3
  при первом запуске подчиненного узла явно включать ОбновлятьАвтоматически методом менеджера.
- Условные предопределенные (зависят от ФО, режима работы): «Не обновлять автоматически», создавать кодом с
  заполнением ИмяПредопределенныхДанных, а в коде учитывать, что элемента может не быть - иначе исключение. В БСП -
  ОбщегоНазначения(Клиент).ПредопределенныйЭлемент, он вернет Неопределено.
```bsl
// обработчик обновления: только в главном узле
Если ПланыОбмена.ГлавныйУзел() = Неопределено Тогда
	ЗаполнитьПредопределенныеВидыЦен();
КонецЕсли;

ВидЦены = ОбщегоНазначения.ПредопределенныйЭлемент("Справочник.ВидыЦен.Закупочная");
Если ВидЦены = Неопределено Тогда
	Возврат;
КонецЕсли;
```

### std638 Работа с неактуальными (недействительными) объектами - [its](https://its.1c.ru/db/v8std/content/638/hdoc)
Рекомендация
- Неактуальные объекты (уволенный сотрудник, расформированное подразделение) не удалять - на них ссылаются. Помечать
  булевым реквизитом Недействителен (по умолчанию Ложь).
- БСП 3.2.2+ с подсистемой «Недействительные объекты»: можно включить объект в общий реквизит Недействителен; другое
  имя реквизита указать в НедействительныеОбъектыПереопределяемый.ПриПолученииНастроекРаботыСНедействительными.
- Скрывать недействительные в автоподборе и быстром выборе. Показать их в конкретном месте - параметр выбора
  ДобавлятьНедействительныеОбъектыВДанныеВыбора (Булево) у реквизита или поля.
- Реализация - ОбработкаПолученияДанныхВыбора в модуле менеджера: есть параметр ДобавлятьНедействительные... -
  убрать отбор Недействителен, иначе отбор = Ложь. При этом выключить историю выбора у таких объектов.
- Предупреждать о выборе недействительного (не помеченного на удаление): элемент ДанныеВыбора - Структура со
  свойствами Значение, ПометкаУдаления, Предупреждение. В БСП - вызов
  НедействительныеОбъекты.ПриОбработкеПолученияДанныхВыбора(Метаданные..., ДанныеВыбора, Параметры, СтандартнаяОбработка).
- Формы списка и выбора: по умолчанию отбор недействительных включен (в ПриСозданииНаСервере, если в параметре Отбор
  нет Недействителен; через ФиксированныеНастройки компоновщика); команда «Показать недействительные» в меню Еще.
- В формах списка/выбора/элемента - команда «Пометить недействительным / Снять пометку» в Еще; в форме элемента
  допустим флажок.
- Пометка на удаление ставит и Недействителен; снятие пометки удаления Недействителен не снимает.
- Отображение в списках - стиль ТекстЗапрещеннойЯчейкиЦвет (192,192,192).
```bsl
Процедура ОбработкаПолученияДанныхВыбора(ДанныеВыбора, Параметры, СтандартнаяОбработка)
	Если Параметры.Свойство("ДобавлятьНедействительныеОбъектыВДанныеВыбора") Тогда
		Параметры.Отбор.Удалить("Недействителен");
	Иначе
		Параметры.Отбор.Вставить("Недействителен", Ложь);
	КонецЕсли;
КонецПроцедуры
```

## Проведение и движения

### std603 Требования к проведению документов - [its](https://its.1c.ru/db/v8std/content/603/hdoc)
Стандарт
- Документ = ввод первичного события. Большинство документов проводятся (Проведение = Разрешить). Непроведенный -
  черновик: можно сохранить незаполненным, без проверок бизнес-логики и дат запрета, в учете не участвует.
  Проведенный - чистовик, отражен в учете.
- Многоэтапный жизненный цикл - статусы поверх проведения: проведение = первичное отражение, статусы уточняют. Для
  проведенного документа переходы по статусам могут требовать дозаполнения и проверок; у черновика статусы не
  контролируются.
- Не проводятся только: (а) регистрационные документы без отражения в учете (корреспонденция, звонки, встречи);
  (б) документы с особой технологией, имитирующие проведение (Операция, Регламентная операция).
- Регистрация + отражение за одно действие - записывать новый документ сразу в режиме проведения; отключать
  проведение для этого запрещено.
- Вторичные данные - в регистры, движения формировать при проведении (автоматически из данных документа или вручную
  - «ручные операции»). Допустимо выносить движения в отдельный документ цепочки (платежное поручение без движений +
  «Списание с расчетного счета» с движениями).
- У непроведенных и помеченных на удаление документов не должно быть активных движений.
- Документ без движений все равно должен проводиться - чтобы отличаться от черновика.
- Перепроведение без изменения влияющих данных (поменяли только Комментарий) не должно менять движения. Исключение -
  движения, формируемые внешними алгоритмами (документ-цепочка).
- Не делать движения зависимыми от состояния регистров (остатков) - иначе результат зависит от порядка ввода.
  Исключение - алгоритмы, суть которых в последовательности (партионный учет).
- Движения строить на данных самого документа. Внешние данные, влияющие на движения (НСИ), либо копировать в
  документ, либо запрещать их изменение (БСП - «Запрет редактирования реквизитов объектов»).
- Минимизировать влияние настроек/ФО на движения: дата начала действия настройки; значения по умолчанию для
  скрытых обязательных полей; писать движения всегда одинаково, а скрывать измерение в отчетах.
- Если зависимость от настройки неустранима - одно из: фоновая обработка после смены настройки (с предупреждением);
  ручная обработка (уведомить при смене и в отчетах); или предупреждение «не менять после начала учета». Реакция на
  включение и выключение может различаться.
- Меняете логику движений - добавьте обработчик обновления ИБ или сохраните старый алгоритм для старых документов.
- Обратимость отражения в учете - через отмену проведения.

### std633 Использование активности движений - [its](https://its.1c.ru/db/v8std/content/633/hdoc)
Стандарт; если в конфигурации переключается активность движений (ручная корректировка)
- В запросах к физическим таблицам таких регистров добавлять условие Активность = ИСТИНА. Виртуальные таблицы
  неактивные записи и так не возвращают.
- Особенно - в универсальных отчетах и логике, работающих с произвольными регистрами.
- При отмене проведения документов с ручной правкой движений (Операция) - выключать активность движений, а не
  удалять их.
```bsl
ВЫБРАТЬ Т.Счет, Т.Сумма ИЗ РегистрБухгалтерии.Хозрасчетный КАК Т
ГДЕ Т.Регистратор = &Ссылка И Т.Активность
```

### std477 Самодостаточность регистров - [its](https://its.1c.ru/db/v8std/content/477/hdoc)
Стандарт
- Регистр логически независим от регистраторов: логика и отчеты по регистру не обращаются к полям регистратора,
  всё нужное хранится в самом регистре.
- Почему: Регистратор.Поле - неявное соединение с таблицами документов; в РИБ движения могут мигрировать без
  регистраторов.

## Изменение структуры метаданных

### std534 Удаление устаревших объектов метаданных из конфигурации - [its](https://its.1c.ru/db/v8std/content/534/hdoc)
Стандарт
- Удаляя объект/реквизит с данными, решить: удалить данные или перенести. При переносе:
  - Не удалять сразу, а переименовать с префиксом Удалить (англ. Obsolete): ОсновнойДоговор -> УдалитьОсновнойДоговор.
    В синоним (и стандартного реквизита тоже) добавить «(не используется) ».
  - Обеспечить перенос данных в новую структуру (обработчик обновления).
  - Документ-регистратор удаляется, а регистры остаются: запретить ему движения при проведении и снятие пометки
    удаления; во всех его движениях заменить регистратор на замещающий документ («Перенос данных», «Операция»);
    пометить все документы этого вида на удаление.
  - Убрать все обращения к устаревшим объектам из конфигурации (кроме кода переноса): исключить из ролей (оставить
    только ПолныеПрава и АдминистраторСистемы), подписок; удалить их код, формы, макеты, команды.
  - Сортировать устаревшие в дереве по общим требованиям к конфигурации.
  - Очистить устаревшие данные; при сложном переносе - через один-два релиза, чтобы оставить шанс на исправление.
- Регистр сведений: удаление измерения или сокращение его типа (уменьшение длины Числа/Строки/Даты, замена типа,
  удаление типа из составного, удаление значения перечисления из типа) грозит ошибкой «Записи регистра стали
  неуникальными». Варианты: новый регистр + перенос + старый в Удалить...; либо «Режим сокращения типа» = «Удалять
  данные», если данные не нужны.
- «Режим сокращения типа» = «Удалять данные» обязателен для измерения с универсальным типом (СправочникСсылка...) и
  для измерений библиотечного регистра, настраиваемых во внедрении (напрямую, через определяемый тип или состав
  перечисления).
- Новый регистр не нужен при добавлении измерения или расширении составного типа.
- Окончательно удалять объекты Удалить... в следующих версиях, если: переход на новые версии возможен только
  последовательно через версию с переносом, либо старой версией уже практически никто не пользуется. Иначе может
  понадобиться промежуточный релиз очистки - чтобы реструктуризация регистров со ссылками на устаревшие данные не упала.
