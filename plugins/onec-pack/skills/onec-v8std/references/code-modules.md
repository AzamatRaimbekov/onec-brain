# Оформление модулей - стандарты 1С (v8std)

> Пересказ раздела «Оформление модулей» системы стандартов its.1c.ru/db/v8std, снят 2026-10-07. Это не копия: при
> сомнении открыть первоисточник по ссылке. Нумерация stdNNN совпадает с сайтом.

Все документы раздела действуют для управляемого, мобильного и обычного приложения.

## Содержание

- std455 Структура модуля (области, их порядок)
- std456 Тексты модулей (язык, «ё», отступы, 120 символов, комментарии)
- std453 Описание процедур и функций (документирующий комментарий)
- std454 Правила образования имен переменных
- std647 Имена процедур и функций
- std640 Параметры процедур и функций
- std641 Структуры и таблицы значений в качестве параметров
- std686 Работа с параметром «Отказ» в обработчиках событий

## Структура и текст модуля

### std455 Структура модуля - [its](https://its.1c.ru/db/v8std/content/455/hdoc)
Стандарт (пп. 2.4.2-2.4.3 и 2.5.1 - методические рекомендации)

Общий порядок разделов в любом модуле (лишние для вида модуля опускаются):
1. заголовок модуля (комментарий);
2. описание переменных;
3. программный интерфейс (экспорт);
4. обработчики событий объекта/формы;
5. служебные процедуры и функции;
6. инициализация.

- Переменных и раздела инициализации не бывает в неглобальных общих модулях, модулях менеджеров, наборов записей,
  менеджеров значений констант и модуле сеанса; обработчики событий элементов - только в модулях форм.
- Каждый раздел и подраздел оформлять как `#Область`; имя области строится по правилам имен переменных (std454).
- Большие разделы делить на подразделы по смыслу (например, `#Область ОбновлениеИнформационнойБазы`).
- Пустые области в модуле не оставлять.

Имена областей по видам модулей (рус. / англ.):

| Вид модуля | Области по порядку |
|---|---|
| Общий модуль | `ПрограммныйИнтерфейс` / `Public`, `СлужебныйПрограммныйИнтерфейс` / `Internal`, `СлужебныеПроцедурыИФункции` / `Private` |
| Модуль объекта, менеджера, набора записей, обработки, отчета | `ОписаниеПеременных` / `Variables`, `ПрограммныйИнтерфейс` / `Public`, `ОбработчикиСобытий` / `EventHandlers`, `СлужебныйПрограммныйИнтерфейс` / `Internal`, `СлужебныеПроцедурыИФункции` / `Private`, `Инициализация` / `Initialize` |
| Модуль формы | `ОписаниеПеременных` / `Variables`, `ОбработчикиСобытийФормы` / `FormEventHandlers`, `ОбработчикиСобытийЭлементовШапкиФормы` / `FormHeaderItemsEventHandlers`, `ОбработчикиСобытийЭлементовТаблицыФормы<ИмяТаблицы>` / `FormTableItemsEventHandlers<FormTableName>` (своя область на каждую таблицу), `ОбработчикиКомандФормы` / `FormCommandsEventHandlers`, `СлужебныеПроцедурыИФункции` / `Private` |
| Модуль команды | `ОбработчикиСобытий` / `EventHandlers` (там `ОбработкаКоманды`), `СлужебныеПроцедурыИФункции` / `Private` |

Назначение разделов:
- **ПрограммныйИнтерфейс** - экспорт для других объектов конфигурации и внешних программ (внешнее соединение).
  В модуле объекта/менеджера сюда НЕ класть экспорт, который вызывается только из самого объекта, его форм и
  команд (например, заполнение ТЧ из формы документа) - это `СлужебныеПроцедурыИФункции`.
- **СлужебныйПрограммныйИнтерфейс** - экспорт, который разрешено звать только из других подсистем той же библиотеки.
- **СлужебныеПроцедурыИФункции** - внутренняя реализация; если модуль входит в подсистему из нескольких объектов,
  здесь же допустим служебный экспорт для вызова только из объектов этой подсистемы.
- **ОбработчикиСобытийЭлементовШапкиФормы** - все элементы вне таблиц формы.
- **ОбработчикиКомандФормы** - процедуры, указанные в свойстве `Действие` команд формы.

Требования к разделам:
- Заголовок модуля - комментарий в первых строках: кратко что за модуль и где применять. В модулях форм в заголовке
  рекомендуется описать параметры формы.
- Каждая переменная модуля снабжается комментарием о назначении, лучше в той же строке.
- Программный интерфейс идет сразу после переменных - «на видном месте».
- Обработчики событий объекта/менеджера - после программного интерфейса, до служебных; рекомендуется в порядке их
  следования в описании встроенного языка.
- Рекомендация: обработчики одного элемента формы держать рядом, в порядке панели свойств конфигуратора.
- Рекомендация: у каждого события - свой обработчик с именем по умолчанию. Общую логику выносить в отдельную
  процедуру и звать ее из каждого обработчика; не вызывать один обработчик из другого (обработчики вызывает платформа,
  смешивание сценариев усложняет код).
- Связанные по смыслу процедуры держать вместе. В модуле формы НЕ группировать методы по директивам
  (клиентские/серверные/без контекста).
- Раздел инициализации - операторы начальной инициализации переменных модуля/объекта.

```bsl
// Неправильно: ПоАвторуПриИзменении вызывает ПоИсполнителюПриИзменении(Неопределено).
&НаКлиенте
Процедура ПоАвторуПриИзменении(Элемент)
	ОбновитьОтборСписка();
КонецПроцедуры

&НаКлиенте
Процедура ПоИсполнителюПриИзменении(Элемент)
	ОбновитьОтборСписка();
КонецПроцедуры
```

### std456 Тексты модулей - [its](https://its.1c.ru/db/v8std/content/456/hdoc)
Стандарт (п. 2 - методическая рекомендация)

- Код пишется на русском. Исключения: имена методов и параметров веб-сервисов (рекомендуются английские) и
  идентификаторы сторонних систем (имена полей внешних структур данных).
- Букву «ё» в коде не использовать. Допустима только в интерфейсных текстах (сообщения, формы, справка).
- Запрещены неразрывные пробелы и «минусы» в других кодировках (короткое/длинное тире) - обычно попадают при
  копировании из офисных документов, ломают поиск, подсказки типов и дают синтаксические ошибки.
- Рекомендация: не оставлять неиспользуемых процедур и функций.
- Не оставлять закомментированный код, отладочный код, служебные пометки (`TODO`, `MRG` и т.п.) и упоминания
  конкретных разработчиков. Пустой обработчик после отладки - удалить целиком.
- Не модифицировать текст запроса через закомментированные фрагменты и `СтрЗаменить` по `//` (см. стандарт оформления
  текстов запросов, п. 6).
- Один оператор - одна строка. Несколько в строке допустимо только для однотипных присваиваний
  (`А = 0; Б = 0; В = 0;`).
- Отступы - табуляцией (не пробелами), размер табуляции 4.
- С левой границы начинаются только: `Процедура/КонецПроцедуры/Функция/КонецФункции`, комментарии-описания методов,
  объявления переменных модуля, код вне методов, директивы компиляции (`&НаКлиенте`...) и аннотации (`&Перед`,
  `&После`...), инструкции препроцессора (включая `#Область`).
- Код между `НачатьТранзакцию()` и `ЗафиксироватьТранзакцию()` дополнительным отступом НЕ сдвигать - это не
  операторные скобки.
- Строки длиннее 120 символов (табуляция = 4) переносить; исключение - когда перенос невозможен (длинная строковая
  константа, выводимая целиком через `СообщениеПользователю`).
- Комментарии - по-русски, деловым сдержанным стилем, только по делу программы. Короткий - в конце строки; длинный -
  отдельной строкой перед фрагментом, выровнен по его левой границе; после `//` обязателен пробел.
- Большие методы можно делить на сворачиваемые области; их имена - по правилам имен переменных.

## Документирование и именование

### std453 Описание процедур и функций - [its](https://its.1c.ru/db/v8std/content/453/hdoc)
Стандарт

Когда комментарий обязателен:
- Обязателен для методов программного интерфейса модулей (их вызывают другие подсистемы/разработчики).
- Прочие методы (включая обработчики событий) комментировать, если нужно пояснить назначение, особенности или
  неочевидную причину, почему что-то НЕ делается. Если все ясно из имени и параметров - можно без комментария.
- Не писать пустых комментариев вида «Процедура - обработчик события ПриОткрытии» или пересказа имени функции.
- В 8.3 текст комментария выводится в контекстной подсказке; в EDT используется для проверки типов.

Формат (комментарий стоит перед объявлением; если есть директива компиляции - сначала комментарий, потом директива):
- **Описание** (`Description`): назначение, достаточное для использования без чтения кода. Начинать с глагола:
  функции обычно «Возвращает...», либо основное действие («Проверяет...», «Вычисляет...»). Не начинать со слов
  «Процедура», «Функция» или с имени самого метода; не повторять имя. Для метода без параметров может быть
  единственной секцией.
- **Параметры:** (`Parameters:`) - каждая строка: `Имя - Тип[, Тип2] - описание`.
  - Тип обязателен. Только существующие типы платформы и спецтипы EDT (`ОпределяемыйТип.<Имя>`, `СправочникСсылка`,
    `ОбъектМетаданныхОтчет` и т.п.). Не писать «КоллекцияЗначений», «ОбъектМетаданных: Отчет», произвольные слова.
  - Текст описания нужен, только если имени мало: формат значения, пример (например, адреса через запятую).
  - `Структура`, `ТаблицаЗначений`, `ДеревоЗначений` - указывать ссылку на функцию-конструктор:
    `- см. МодульКлиентСервер.ПараметрыЧегоТо`. Просто тип допустим, только если метод универсально обрабатывает коллекцию.
  - `Массив` - указывать тип элементов через «из»: `Массив из СправочникСсылка.Номенклатура`,
    `Массив из см. Модуль.Конструктор`. Без типа элементов - только для универсальных методов (как
    `ДополнитьМассив` в БСП).
  - `СтрокаТаблицыЗначений`/`СтрокаДереваЗначений` - можно указать колонки ссылкой:
    `СтрокаТаблицыЗначений: см. Модуль.ФункцияВозвращающаяТаблицу`.
  - Дополнительные варианты типа параметра - новые строки, начинающиеся с `- Тип - описание`.
  - Ссылки `см. ...` допустимы на реквизиты объекта/формы (`см. Обработка.Х.ТабличнаяЧасть.Y`,
    `см. Документ.Х.ФормаДокумента.Объект.Y`), а в редком случае без конструктора - на параметр другого метода.
  - Если метод - реализация события из программного интерфейса (переопределяемый модуль) с тем же составом
    параметров, достаточно одной строки `// См. МодульПереопределяемый.ИмяСобытия`.
- **Возвращаемое значение:** (`Returns:`) - только у функций; с новой строки `Тип - описание`. Составной тип - каждый
  тип с новой строки через `- `. Массив - как у параметров; структуры и таблицы - по std641 (свойства через `*`).
- **Пример:** (`Example:`) - вызов с именем общего модуля, видно вход и выход. В переопределяемых модулях - пример
  реализации процедуры, а не ее вызова.
- **Варианты вызова:** (`Call options:`) - в редких случаях, когда несколько параметров имеют альтернативные типы:
  `ИмяМетода(Тип1, Тип2) - описание` на каждой строке.
- Отступы: текст объявляемых секций сдвинут относительно заголовка секции; во многострочном описании одного пункта
  доп. отступ только у второй строки, дальше строки выровнены по второй.
- В любом месте можно ставить переходы `См. Модуль.Метод` (EDT делает гиперссылку).
- Устаревший метод: первая строка описания начинается со слова «Устарела.» (`Deprecated.`) и указывает замену.
- Методы в модуле отделять друг от друга пустыми строками.

```bsl
// Возвращает остаток товара на складе на дату.
//
// Параметры:
//   Номенклатура - СправочникСсылка.Номенклатура
//   Склад - СправочникСсылка.Склады
//   Дата - Дата - момент расчета; пустая дата означает текущий остаток.
//
// Возвращаемое значение:
//   Число - остаток в базовых единицах.
//
// Пример:
//   Остаток = ЗапасыСервер.ОстатокНаСкладе(Товар, ОсновнойСклад, '00010101');
//
Функция ОстатокНаСкладе(Номенклатура, Склад, Дата) Экспорт
```

### std454 Правила образования имен переменных - [its](https://its.1c.ru/db/v8std/content/454/hdoc)
Стандарт
- Имя строить из терминов предметной области так, чтобы было понятно назначение.
- Слова слитно, каждое с прописной (включая однобуквенные предлоги: `ДиалогРаботыСКаталогом`).
- Без сокращений-венгерки: `масРеквизитов`, `соотвВидИмя`, `новСтр` - неправильно.
- Не начинать с подчеркивания.
- Не использовать имена из одного символа - кроме счетчиков циклов.
- Флаги называть по истинному значению: `ЕстьОшибки`, `ЭтоТоварТара`.

### std647 Имена процедур и функций - [its](https://its.1c.ru/db/v8std/content/647/hdoc)
Стандарт (пп. 4-6 - методические рекомендации)
- Имена методов и параметров - «говорящие», из терминов предметной области; трудность подбрать имя - признак плохой
  архитектуры. Неправильно: `ВыполнитьПроверку(Параметр1, Рекв, ТЗ)`.
- Слова слитно, каждое с прописной (как std454).
- Рекомендации:
  - Не вписывать в имя тип параметров/результата: `ИменаРолейСПравомДобавления()`, а не
    `ПолучитьМассивРолей...()` (исключение - когда без типа непонятен смысл).
  - Процедура - глагол в неопределенной форме: `ЗагрузитьКонтрагента`, а не `ЗагрузкаКонтрагента`.
  - Функция - по описанию результата, без «Получить/Определить/Создать»: `ПолноеИмяПользователя()`,
    `ДатаНачалаСеанса()`.
  - Функция-создатель объекта - со словом «Новый»: `НовоеПолеФормы()`, `НоваяТаблицаКоманд()`.
  - Функция-проверка - с «Это» или причастием: `ЭтоВнешняяЗадача()`, `ДокументПроведен()`.
  - Глагол в имени функции уместен, когда важно, как получен результат: `ВыбратьДанныеПоПравилу(...)`.
  - Если главное в функции - действие, а результат вторичен (признак успеха), имя - глагол, как у процедуры:
    `РазрешитьРедактированиеРеквизитовОбъекта(Форма)`.

## Параметры и обработчики

### std640 Параметры процедур и функций - [its](https://its.1c.ru/db/v8std/content/640/hdoc)
Стандарт
- Имена параметров - по правилам имен переменных (std454).
- Не передавать данные в метод в обход параметров (через переменные модуля, реквизиты формы и т.п.).
- Порядок параметров - логический, от общего к частному: `ПоменятьЦветПоляФормы(Форма, ИмяПоля, Цвет)`.
- Необязательные параметры (со значением по умолчанию) - после обязательных.
- Ориентир: не более 7 параметров, из них не более 3 необязательных. Иначе - группировать однородные параметры в
  `Структура` (ДанныеЗаполнения, ПараметрыПроведения...) или разбить метод на более простые (например, функция
  `НовоеПолеФормы(ИмяПоля)` + присваивание свойств вызывающим кодом).
- Не делать вложенных вызовов функций в параметрах, если строка становится громоздкой/требует переноса - выносить во
  вспомогательные переменные. Короткие читаемые вложения допустимы.
- Не передавать в параметр `Новый Структура("...", ...)` с большим числом свойств (ориентир - не более 3); иначе
  собрать структуру заранее через `Вставить`.
- При вызове нет пробелов: перед `(`, после `(`, перед `)`, перед запятой (если параметры в одной строке и не опущены).
  Правильно: `НовоеПолеФормы(ИмяПоля, ТипПоля)`.
- Не пропускать обязательные параметры при вызове (придет `Неопределено`). Если `Неопределено` допустимо - передавать
  явно или сделать параметр необязательным со значением по умолчанию `Неопределено`.

### std641 Структуры и таблицы значений в качестве параметров - [its](https://its.1c.ru/db/v8std/content/641/hdoc)
Стандарт
- Для метода с параметром `Структура`, `ТаблицаЗначений` или `ДеревоЗначений` заводить функцию-конструктор, которая
  возвращает заготовку структуры со всеми свойствами или пустую таблицу/дерево с типизированными колонками; вызывающий
  код заполняет ее и передает.
- Свойства структуры соответствуют параметрам вызываемого метода; необязательные параметры явно инициализировать
  значениями по умолчанию в конструкторе.
- Для таблицы значений конструктор можно не делать, если таблица - результат вычислений прикладного кода (например,
  выгрузка запроса передается дальше).
- В программном интерфейсе библиотек каждая функция, возвращающая структуру/таблицу (в т.ч. конструкторы), обязана
  описывать возвращаемое значение: свойства/колонки с новой строки, с префиксом `*`; вложенные уровни - `**`, `***`...
- Вызывающий код не создает структуру параметров сам, не добавляет в нее свойств и не меняет состав/типы колонок
  таблицы - все допустимые параметры определены только в конструкторе.

```bsl
// Возвращает параметры для ЦенообразованиеСервер.ЗаполнитьЦены.
//
// Возвращаемое значение:
//   Структура:
//     * Дата - Дата
//     * ВидЦены - СправочникСсылка.ВидыЦен
//     * ПересчитатьСумму - Булево
//
Функция ПараметрыЗаполненияЦен() Экспорт
	Результат = Новый Структура;
	Результат.Вставить("Дата", ТекущаяДатаСеанса());
	Результат.Вставить("ВидЦены", Справочники.ВидыЦен.ПустаяСсылка());
	Результат.Вставить("ПересчитатьСумму", Истина);
	Возврат Результат;
КонецФункции
```

### std686 Работа с параметром «Отказ» в обработчиках событий - [its](https://its.1c.ru/db/v8std/content/686/hdoc)
Стандарт
- В обработчиках с параметром `Отказ` (`ПередЗаписью`, `ОбработкаПроверкиЗаполнения`, `ТоварыПередНачаломДобавления`
  и т.п.) никогда не присваивать `Отказ = Ложь` - его могли уже взвести предыдущие проверки или подписки.
  Писать `Если <ошибка> Тогда Отказ = Истина; КонецЕсли;` или `Отказ = Отказ Или <ошибка>;`.
  Неправильно: `Отказ = ЕстьОшибкиЗаполнения();`.
- То же для `СтандартнаяОбработка`, `Выполнение` и подобных: только переводить в «отказное» значение по условию.
- В `ПриЗаписи`, `ПередЗаписью`, `ПередУдалением`, `ОбработкаПроведения`, `ОбработкаПроверкиЗаполнения` и т.п. не
  устанавливать `Отказ = Истина` молча - сообщить причину (`ОбщегоНазначения.СообщитьПользователю(..., Отказ)`) или
  вызвать исключение; иначе пользователь видит лишь «Не удалось записать...».

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)
	Если Не ТоваровДостаточно() Тогда
		ОбщегоНазначения.СообщитьПользователю(
			НСтр("ru = 'Недостаточно товара на складе.'"), , "Объект.Товары", , Отказ);
	КонецЕсли;
КонецПроцедуры
```
