# Права доступа к данным - стандарты 1С (v8std)

> Пересказ раздела «Настройка прав доступа к данным» системы стандартов its.1c.ru/db/v8std, снят 2026-10-07. Это не
> копия: при сомнении открыть первоисточник по ссылке. Нумерация stdNNN совпадает с сайтом.

Содержание:
- std488 Стандартные роли
- std689 Настройка ролей и прав доступа (УП/ERP, УТ 11)
- std532 Установка прав для новых объектов и полей объектов
- std485 Использование привилегированного режима
- std737 Проверка прав доступа
- std415 Ограничения на использование ключевого слова «РАЗРЕШЕННЫЕ» в запросах
- std491 Влияние изменения параметров сеанса и ФО на производительность ограничения доступа

Область применения всех документов раздела: управляемое и обычное приложение.

## Роли

### std488 Стандартные роли - [its](https://its.1c.ru/db/v8std/content/488/hdoc)
Стандарт (п.2.5 - методическая рекомендация)
- Разграничение доступа делать ролями. Роли - либо по должностям (Директор, Бухгалтер), либо мелкие функциональные
  (ЧтениеНСИ ...) с поставкой готовых комбинаций-профилей (в БСП - «Управление доступом»).
- Обязательные роли, все три - в свойстве конфигурации `ОсновныеРоли`:
  - `ПолныеПрава` (FullAccess, синоним «Полные права»): назначается самостоятельно; полный доступ ко всем прикладным
    (разделенным) данным, кроме интерактивного удаления; все административные действия в области данных. Обязательно
    содержит права: Администрирование данных, Активные пользователи, Журнал регистрации, Монопольный режим, Тонкий
    клиент, Веб-клиент, Сохранение данных пользователя, Вывод. В сервисе - администраторам абонентов; локально -
    вместе с `АдминистраторСистемы`.
  - `АдминистраторСистемы` (SystemAdministrator): только вместе с `ПолныеПрава`; доступ ко всем неразделенным данным;
    все права на объекты (кроме интерактивного удаления) и все права на корень (в т.ч. Администрирование,
    Администрирование данных), кроме интерактивного открытия внешних отчетов и обработок.
  - `ИнтерактивноеОткрытиеВнешнихОтчетовИОбработок` (InteractiveOpenExternalReportsAndDataProcessors): только права
    корня «Интерактивное открытие внешних отчетов/обработок». Локально - админам (админ может запретить); в сервисе все
    три роли - админам сервиса.
- Рекомендация: для удаления объектов «неполноправными» - отдельная несамостоятельная роль `УдалениеПомеченныхОбъектов`
  (DeleteMarkedObjects).
- Общие права ИБ - отдельные несамостоятельные роли; конфигурация обязана работать и с ними, и без любой из них:
  `Администрирование` (Administration: Администрирование, Администрирование данных, Администрирование расширений,
  Активные пользователи), `ВыводНаПринтерФайлБуферОбмена` (Вывод), `ЗапускAutomation`, `ЗапускВебКлиента`,
  `ЗапускВнешнегоСоединения`, `ЗапускТолстогоКлиента`, `ЗапускТонкогоКлиента`,
  `ИнтерактивноеОткрытиеВнешнихОтчетовИОбработок`, `ОбновлениеКонфигурацииБазыДанных`, `ПросмотрЖурналаРегистрации`,
  `РежимТехническогоСпециалиста` (все штатные обработки должны быть доступны без него), `СохранениеДанныхПользователя`.
- `СохранениеДанныхПользователя` давать почти всем; конфигурация должна работать без него: код, пишущий/читающий
  хранилища настроек (`ХранилищеОбщихНастроек`, `ХранилищеВариантовОтчетов`, `ХранилищеНастроекДанныхФорм`,
  `ХранилищеПользовательскихНастроекОтчетов`, `ХранилищеСистемныхНастроек`), `ИсторияРаботыПользователя`,
  `ИзбранноеРаботыПользователя`, `УстановитьТекущиеПользовательскиеНастройки`, при отсутствии права пропускается без
  влияния на основные сценарии; элементы вида «Запомнить мой выбор» скрываются. С БСП -
  `ОбщегоНазначения.ХранилищеОбщихНастроекЗагрузить`/`ХранилищеОбщихНастроекСохранить`.
- Для просмотра всех данных (аудитор, собственник) - отдельные роли: при должностных ролях - `ТолькоПросмотр` (ViewOnly:
  Чтение, Использование, Просмотр, Ввод по строке на большинство объектов, кроме технологических); при мелких ролях -
  комбинация ролей чтения и поставляемые профили; RLS у таких ролей не задавать.
- Ни в одной роли (включая полные) не ставить: Интерактивное удаление, Интерактивное удаление/пометка удаления/снятие
  пометки/удаление помеченных предопределенных данных - кроме обоснованных случаев. Право «Удаление» - только у
  `ПолныеПрава` и `АдминистраторСистемы`.
- Расширения: не заимствовать и не менять `ПолныеПрава`/`АдминистраторСистемы`, а добавлять свои:
  - одинаковые права для всех - `<Префикс>ОбщиеПрава` (в основные роли расширения);
  - админ/пользователи - `<Префикс>ПолныеПрава` (в основные роли) + `<Префикс>БазовыеПрава`;
  - плюс внешние пользователи - еще `<Префикс>БазовыеПраваВнешнихПользователей`.
  - В БСП они автоматически попадают в профили: ОбщиеПрава - в профили с `БазовыеПраваБСП`,
    `БазовыеПраваВнешнихПользователейБСП`, `ПолныеПрава`; БазовыеПрава - с `БазовыеПраваБСП`;
    БазовыеПраваВнешнихПользователей - с `БазовыеПраваВнешнихПользователейБСП`; ПолныеПрава - с `ПолныеПрава`.
    Прочие прикладные роли расширения в профили сами не попадают (дописать программно или вручную). Без БСП -
    назначать эти роли пользователям программно/интерактивно.

### std689 Настройка ролей и прав доступа - [its](https://its.1c.ru/db/v8std/content/689/hdoc)
Стандарт для УП (ERP), УТ 11 и их библиотек; для остальных - рекомендуется
- Роли атомарные (элементарные функции); пользователям назначаются профили из них средствами БСП; на типовом внедрении
  не должно требоваться новых ролей. Исключение - роли внешних пользователей задают исчерпывающий набор прав.
- `ПолныеПрава` + `АдминистраторСистемы` = доступ ко всему без RLS.
- Ни одна роль не дает интерактивного удаления ссылочных объектов (после добавления объекта - снять в `ПолныеПрава`);
  право «Удаление» ссылочных - только у `ПолныеПрава`/`АдминистраторСистемы`.
- «Устанавливать права для новых объектов» - только у `ПолныеПрава`.
- Права, нужные только админу (отчет, обработка), - только в `ПолныеПрава`/`АдминистраторСистемы`, без отдельной роли.
- Все проводимые документы - с флагами «Привилегированный режим при проведении» и «...при отмене проведения»; ролей на
  изменение подчиненных регистров не делать. Исключение - документы ручной корректировки регистров (тогда нужны роли на
  изменение регистров).
- Все ФО - с «Привилегированный режим при получении». Исключение - параметризованные ФО, где различие по правам
  задумано намеренно.
- Общие права (Администрирование, ТонкийКлиент...) - только в стандартных ролях БСП; в новых ролях выключать.
- Неконфиденциальное и общедоступное (константы, общенациональные классификаторы, общие формы выбора периода, ввода КИ)
  - права чтения/просмотра/ввода по строке в `БазовыеПрава<Библиотека>` и `БазовыеПраваВнешнихПользователей<Библиотека>`
  (последняя - если есть внешние пользователи).
- Роль не дает прав на объекты разных подсистем/библиотек.
- Элементарные функции: объединять объекты, доступ к которым не может различаться (документ + его регистр-«отражение» +
  отчет по нему); при сомнении - разделять; каждый объект ровно в одной функции; объекты разных библиотек - в разных.
- Для ссылочных объектов и независимых РС - две роли:
  - `Чтение<Функция>` (Read): Чтение, Просмотр, Ввод по строке;
  - `Изменение<Функция>` (Edit, если добавление автоматическое/админское) = Чтение + Изменение, Редактирование;
    для документов Проведение, Отмена проведения, Интерактивное проведение/отмена, Интерактивное изменение проведенных;
    для регистров Управление итогами; с БСП 3.2.2+ Чтение/Просмотр истории данных, Изменение/Редактирование
    комментария версии истории данных;
  - `ДобавлениеИзменение<Функция>` (AddEdit) = Изменение + Добавление, Интерактивное добавление, Интерактивная
    пометка/снятие пометки удаления.
  - Подчиненным регистратору регистрам права изменения обычно не нужны.
- Журналы документов: если все документы журнала в одной функции - чтение/просмотр журнала во все роли функции;
  отдельную роль на журнал не делать (без права на любой документ журнала графы закрываются для всех).
- Константы: меняет только админ - права изменения только в `ПолныеПрава` или `АдминистраторСистемы` (с чтением);
  меняет пользователь - в «настроечную» роль или `Изменение<Константа>`; чтение обычных констант - в
  `БазовыеПрава<Библиотека>` (чтобы не включать привилегированный режим для чтения); конфиденциальные - роль
  `Чтение<Константа>`, если не только для админа.
- Подсистема верхнего уровня - роль `Подсистема<Имя>` (Subsystem) с правом просмотра, включая форму «Настройки и
  справочники» раздела, если есть.
- Отчеты: по данным одной функции - в роли функции; если на внедрении нужен отдельный доступ или данные из нескольких
  функций - `ПросмотрОтчета<Имя>` (ViewReport: Использование, Просмотр). Однотипные отчеты можно объединить в функцию,
  если не входят в другие функции и не потребуют разных прав.
- Обработки: рабочее место (своя команда в ГКИ) - `ИспользованиеОбработки<Имя>` (UseDataProcessor), одна роль на одну
  обработку; вспомогательные (подбор, общий код печати) - в `БазовыеПрава<Библиотека>`; админские - только в
  `ПолныеПрава` (или `АдминистраторСистемы`, если работают только без разделителя). Общие формы - так же,
  `ИспользованиеОбщейФормы<Имя>` (UseCommonForm).
- Команды: без изменения данных - в роль просмотра объекта и в роль изменения; команды печати из обработок - в
  `БазовыеПрава<Библиотека>`; изменяющие данные - в роль изменения.
- Дополнительные права, не связанные с объектами: роль `<НазваниеПрава>` без прав на объекты, без слова «Право» в имени
  (`ОтклонениеОтУсловийЗакупок`, не `ПравоСоздания...`). Проверять через `Пользователи.РолиДоступны` (полноправный
  проходит без роли). Иные механизмы допправ запрещены.
- Роли только для внешних пользователей - с префиксом (например, `Самообслуживание...`).
- Объекты с префиксом `Удалить` - исключить из всех ролей, кроме `ПолныеПрава`/`АдминистраторСистемы`.

### std532 Установка прав для новых объектов и полей объектов - [its](https://its.1c.ru/db/v8std/content/532/hdoc)
Стандарт
- Цель - не допустить ролей, дающих права на поля, но не на сам объект (на внедрении это может случайно открыть все
  реквизиты).
- «Устанавливать права для новых объектов» - только у `ПолныеПрава`.
- В новой роли: «Устанавливать права для реквизитов и табличных частей по умолчанию» - включен, «Независимые права
  подчиненных объектов» - выключен.
- Если нужны права только на поля (реквизиты, ТЧ, измерения, команды) без прав на объект - сначала включить
  «Независимые права подчиненных объектов», выключить «...по умолчанию» с очисткой прав на все реквизиты и ТЧ.
- Добавляя объект или поле - сразу настраивать права в соответствующих ролях.

## Привилегированный режим и проверка прав

### std485 Использование привилегированного режима - [its](https://its.1c.ru/db/v8std/content/485/hdoc)
Стандарт
- Применять, когда проверку прав логически нужно отключить, или для ускорения, если это не дает пользователю ничего
  сверх его прав.
- Типовые сценарии: подчиненные регистры, нужные для отчетов, - пользователю только чтение, запись при проведении в
  привилегированном режиме (права проверяются только на регистратор); служебные регистры (например, `ВерсииПодсистем`)
  - без прав вообще, доступ через функции в привилегированном режиме; недоступные пользователю данные для разрешенной
  операции - читать привилегированно, не отдавая их на клиент и используя только для этой операции; ускорение запроса,
  параметры которого уже прошли RLS-проверку (для отчетов - очень осторожно); чтение параметра сеанса
  `ТекущийПользователь`, недоступного ролям.
- Опасно: экспортный метод, безусловно включающий привилегированный режим (особенно доступный клиенту). Исключение -
  действие/результат разрешены абсолютно всем.
- При недостатке прав должно выпадать стандартное исключение; обычно его даст сама платформа (запрос без
  `РАЗРЕШЕННЫЕ`, `ПолучитьОбъект` по недоступной ссылке, недоступный метод). Ручная проверка перед привилегированным
  блоком - `ВыполнитьПроверкуПравДоступа`.
- Включать точечно: включить прямо перед действием, выключить сразу после, остальной код - с проверкой прав.
- Способы: свойства документа «Привилегированный режим при проведении» / «...при отмене проведения» (если состав
  выборки в проведении должен зависеть от прав пользователя - снять их и использовать `УстановитьПривилегированныйРежим`);
  свойство БП «Привилегированный режим» (создание задач); свойство ФО «Привилегированный режим при получении»;
  `УстановитьПривилегированныйРежим(Истина/Ложь)`; общий модуль с признаком «Привилегированный».

```bsl
Процедура ИзменитьДанные(Знач Ссылка) Экспорт
	ВыполнитьПроверкуПравДоступа("Изменение", Ссылка.Метаданные());
	// подготовка - с проверкой прав
	УстановитьПривилегированныйРежим(Истина);
	ЗаписатьСлужебныеДанные(Ссылка);
	УстановитьПривилегированныйРежим(Ложь);
КонецПроцедуры
```

### std737 Проверка прав доступа - [its](https://its.1c.ru/db/v8std/content/737/hdoc)
Стандарт
- При большом числе ролей (от нескольких десятков) не использовать ролевую настройку в элементах форм (просмотр/
  редактирование реквизитов по ролям, видимость полей по ролям, использование команд по ролям). Сильные различия -
  отдельные формы под набор прав; слабые - проверка прав в коде (учитывая замедление открытия формы).
- Не использовать ролевую видимость в командном интерфейсе конфигурации, основного раздела и начальной странице - вместо
  этого права на разделы, общие формы и объекты.
- Проверять права в коде через `ПравоДоступа("Редактирование", Метаданные.Справочники.X)`, а не `РольДоступна("ИмяРоли")`
  (устойчиво к перекройке ролей).
- `РольДоступна` - только для ролей-допправ без прав на объекты; проверять вместе с полноправностью и
  `ПривилегированныйРежим()`. С БСП - `Пользователи.РолиДоступны(...)`.
- Если данные читаются/пишутся привилегированно, не добавлять в роль фиктивные права с RLS `ГДЕ ЛОЖЬ` ради
  `ПравоДоступа` - проверять роль (`Пользователи.РолиДоступны`); при этом допустимо подавить проверку АПК комментариями
  `// АПК:515-выкл` ... `// АПК:515-вкл` с обоснованием.

```bsl
Если ПравоДоступа("Просмотр", Метаданные.Отчеты.АнализПродаж) Тогда
	Элементы.ОткрытьАнализ.Видимость = Истина;
КонецЕсли;
```

## Запросы и производительность RLS

### std415 Ограничения на использование ключевого слова «РАЗРЕШЕННЫЕ» в запросах - [its](https://its.1c.ru/db/v8std/content/415/hdoc)
Стандарт
- Не добавлять `РАЗРЕШЕННЫЕ` во все запросы «чтобы не падало»: в бизнес-логике это молча искажает результат (например,
  себестоимость списания будет разной у разных пользователей).
- Для учетных механизмов: либо дать пользователю право на нужные данные, либо прервать операцию с сообщением о
  нарушении прав. `РАЗРЕШЕННЫЕ` уместно там, где неполнота данных не влияет на логику (например, показ контактной
  информации).

### std491 Влияние изменения параметров сеанса и ФО на производительность ограничения доступа - [its](https://its.1c.ru/db/v8std/content/491/hdoc)
Стандарт
- Платформа кэширует запросы ограничений доступа с текущими значениями параметров сеанса и ФО; их изменение сбрасывает
  кэш и сильно замедляет запросы.
- Устанавливать параметры сеанса «по требованию» в `УстановкаПараметровСеанса` модуля сеанса; не менять часто значения
  ФО в процессе работы.
