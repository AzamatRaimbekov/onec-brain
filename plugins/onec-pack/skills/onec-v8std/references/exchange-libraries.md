## Реализация обмена данными

### std637 Настройка обмена классификаторами между разными ИБ - [its](https://its.1c.ru/db/v8std/content/637/hdoc)
Стандарт; управляемое и мобильное приложение. Касается обменов, сделанных в «Конвертации данных».
- Классификатор = справочник или регистр сведений с условно-постоянными данными, одинаковыми во всех базах
  (банки, страны, валюты, ОКЕИ, адресный классификатор).
- Объектные классификаторы сопоставлять сначала по UUID ссылки, затем по полям поиска. В ПКО включить оба флага:
  «Искать объект приемника по внутреннему идентификатору объекта источника» и «Продолжить поиск по полям
  поиска, если по идентификатору объект приемник не найден»; задать ПКС полей поиска (например, БИК для банков);
  для сложной идентификации - обработчик ПКО «Поля поиска». Иначе - дубли (UUID в разных базах обычно разные).
- Классификаторы-наборы записей (например, адресный) в обмен НЕ включать: каждая база заполняет и обновляет их сама.

### std701 Разработка планов обмена с отборами - [its](https://its.1c.ru/db/v8std/content/701/hdoc)
Рекомендация; управляемое и мобильное приложение.
- Узлы-получатели определять логикой регистрации в событиях `ПередЗаписью` / `ПередУдалением` объектов. В БСП
  («Обмен данными») логику можно задать декларативно правилами регистрации объектов (ПРО) из «Конвертации данных».
- Учитывать при проектировании логики регистрации:
  - объекты из сообщения обмена грузятся в произвольном порядке - нужные данные могут ещё отсутствовать;
  - логика регистрации работает и при загрузке, внутри транзакции записи, `ОбменДанными.Загрузка` её не отключает -
    любое исключение обрушит загрузку всего сообщения;
  - в РИБ мигрирует не всё (движения могут прийти без регистратора);
  - обращение к полям связанных таблиц «через точку» - неявные соединения, обмен тормозит.
- Для обменов по правилам конвертации через БСП (не РИБ) первые два пункта для ссылочных типов можно не учитывать:
  ссылочные объекты регистрируются отложенно после загрузки всего сообщения.
- Правила:
  1. Самодостаточность: каждая таблица в обмене содержит все поля для своей регистрации (например, ссылку на
     организацию); логика читает только поля своей таблицы, без связанных.
  2. Если самодостаточность невозможна - исключить из плана обмена вторичные данные, которые можно вычислить в
     каждой базе самостоятельно (например, служебный регистр прав доступа).
  3. Для логически связанных таблиц регистрировать к выгрузке все связанные данные при записи любой из них;
     при нехватке данных не падать, а пропускать регистрацию (зарегистрируется при загрузке недостающей части).

### std771 Интеграция прикладных решений через формат EnterpriseData - [its](https://its.1c.ru/db/v8std/content/771/hdoc)
Стандарт (п.5 - рекомендация); управляемое приложение.
- Переходы конфигурация -> конфигурация делать на правилах конвертации (ПК). Обмены между конфигурациями на БСП - только
  через EnterpriseData. Новые обмены на ПК разрабатывать запрещено; исключение - решения для бюджетных организаций.
- Актуальные версии формата - пакеты XDTO в последней БСП с именами `EnterpriseData_X_Y_Z` (X.Y - major, Z - minor).
- Поддерживать в обмене все версии формата, которые поддерживает встроенная версия БСП; выпускать конфигурацию без
  поддержки хотя бы одной из них запрещено (пример: БСП 2.4.1 -> версии 1.2, 1.3, 1.4).
- Исключение: не поддерживать версию формата, если в ней нет нужной обмену функциональности (например, «Чек ККМ»
  есть только с 1.4 -> минимум 1.4).
- Рекомендация: сообщать пользователям, какие версии EnterpriseData поддерживает решение.
- В типовых обменах не передавать данные через свойство `AdditionalInfo`; новые свойства - только согласованным
  изменением формата. Допустимо лишь: срочная поддержка законодательства без времени на новую версию формата и обход
  критических ошибок, блокирующих синхронизацию. Помнить: такой сценарий придётся долго поддерживать.

### std799 Разработка правил регистрации - [its](https://its.1c.ru/db/v8std/content/799/hdoc)
Стандарт; управляемое и мобильное приложение.
- Правила регистрации (проверки и отборы данных для синхронизации) размещать в модулях конфигурации, например общим
  модулем «менеджер регистрации», а не во внешних файлах правил: так их проверяет синтаксис-контроль, проще отладка,
  выпуск исправлений, перевод кода.
- В правилах регистрации запрещено переключать привилегированный и безопасный режимы (`УстановитьПривилегированныйРежим`,
  `УстановитьБезопасныйРежим` и аналоги).
- Исправления ошибок в правилах обмена поставлять расширениями (патчами).

## Разработка и использование библиотек

### std551 Повторное использование общего кода и объектов метаданных - [its](https://its.1c.ru/db/v8std/content/551/hdoc)
Методическая рекомендация; все виды приложений.
- Общий для линейки продуктов код выносить в библиотечную конфигурацию (не для конечных пользователей) и подключать
  постановкой на поддержку.
- Библиотеки могут образовывать иерархию (библиотека-наследник на поддержке у библиотеки-родителя); конечные
  потребители - прикладные решения.
- Различать области видимости кода:
  1. Программный интерфейс - экспорт для внешних потребителей: (а) для любого места/расширений/других программ;
     (б) для конкретных потребителей - в подразделе «Для вызова из других подсистем».
  2. Служебный программный интерфейс - экспорт только для других подсистем той же библиотеки.
  3. Служебные процедуры и функции - внутренняя реализация; экспорт только для объектов той же подсистемы.

### std552 Имена объектов метаданных в иерархии библиотек - [its](https://its.1c.ru/db/v8std/content/552/hdoc)
Стандарт; все виды приложений.
- Не допускать конфликтов имён между объектами библиотек и конфигурации. Приоритет имени - у библиотеки нижнего
  уровня; конфликтующий объект потребителя переименовать более конкретно (`Настройки` ->
  `НастройкиУправленческогоУчета`).
- Называть объекты предметно, не «универсально». Самые общие имена (`ОбщегоНазначения`, `СтроковыеФункции`)
  - только в библиотеках самого нижнего уровня; выше - специфичные (`ЗарплатаКадры`, `ПроведениеСкладскихДокументов`).
- Объекты, расширяющие функциональность нижней библиотеки или конфликтующие с соседней, именовать с постфиксом
  библиотеки/конфигурации: `ОбновлениеИнформационнойБазыМФ`, `СтроковыеФункцииРегл`,
  `РаботаСФормамиЗарплатаКадры` (то же для подписок на события).

### std553 Переопределяемые и поставляемые объекты библиотеки - [its](https://its.1c.ru/db/v8std/content/553/hdoc)
Стандарт; все виды приложений.
- Категории объектов библиотеки и правило поставки:
  - непереопределяемые (используются как есть, обязаны присутствовать; пример - справочник `Пользователи`) -
    «изменения не рекомендуются»; срочные правки допустимы, но документировать/передать разработчикам библиотеки,
    иначе потеряются при обновлении;
  - переопределяемые (настраивают библиотеку под потребителя) - «изменения разрешены»;
  - определители типов (общее имя, своя реализация в каждом потребителе: `Организации`) - «изменения разрешены».
- Минимизировать число переопределяемых объектов: расширять состав типов (общих команд, измерений составного типа),
  параметризовать предопределёнными элементами, менять поведение через переопределяемые общие модули
  (обработчики событий библиотеки вида `ПриДобавленииОбработчиковОбновления`).
- Имя переопределяемого общего модуля - с постфиксом `Переопределяемый`.
- Переопределяемый модуль содержит только экспортные процедуры, которые вызывает сама библиотека. Потребитель
  НЕ вызывает переопределяемый модуль напрямую - только непереопределяемый модуль библиотеки
  (`ПапкиФайлов`, а не `ПапкиФайловПереопределяемый`). Программный интерфейс библиотеки = экспорт
  непереопределяемых модулей.
- В поставке переопределяемые процедуры имеют пустое тело; неэкспортных методов там нет. Значения по умолчанию
  заполняет библиотека до вызова переопределяемой процедуры.
```bsl
// Модуль библиотеки (непереопределяемый)
Функция ПараметрыПодсистемы() Экспорт
	Параметры = Новый Структура("ПоказыватьИтоги", Ложь); // умолчания - здесь
	МояБиблиотекаПереопределяемый.ПриОпределенииПараметров(Параметры);
	Возврат Параметры;
КонецФункции
// МояБиблиотекаПереопределяемый: Процедура ПриОпределенииПараметров(Параметры) Экспорт <пусто> КонецПроцедуры
```
- При обновлении библиотеки вручную сверять модули корня конфигурации и переопределяемые модули: перенести новые
  процедуры, удалить устаревшие, сверить комментарии, число и имена параметров с библиотечными.

### std554 Переопределение общих модулей в иерархии библиотек - [its](https://its.1c.ru/db/v8std/content/554/hdoc)
Методическая рекомендация; все виды приложений.
- Переопределяемый модуль объявляет библиотека нижнего уровня (`БазоваяБиблиотекаПереопределяемый`).
- Библиотека верхнего уровня кладёт в процедуру этого модуля не реализацию, а один вызов своего модуля, обрамлённый
  комментариями `// Начало: <Библиотека>` / `// Конец: <Библиотека>`. Следующий уровень добавляет свой блок ниже.
- Конечная конфигурация видит цепочку вызовов и дописывает свой код после них; любой блок можно убрать.

### std644 Обеспечение совместимости библиотек - [its](https://its.1c.ru/db/v8std/content/644/hdoc)
Стандарт; все виды приложений.
- Обратная совместимость обязательна в пределах подредакции (2.0.1, 2.0.2, 2.0.5 совместимы; 2.1 может ломать).
- Номер РР.ПП.ВВ.СС:
  - РР - редакция, серьёзная несовместимость;
  - ПП - подредакция: ломается совместимость, нужна инструкция по переходу, удаляются устаревшие объекты;
  - ВВ - только новые функции, инструкция не обязательна, допустима механическая автозаливка;
  - СС - только исправления ошибок.
- Исключения (заранее согласованные): изменения законодательства (исправительные сборки во все поддерживаемые ветки,
  поломка совместимости документируется и обязательна к отработке) и LTS-версии.
- Устаревшие объекты удалять не чаще раза в год, в версиях ближе к концу года; объект живёт не менее 2 лет. Такая
  версия помечается обязательной для перехода; суммарно по всем библиотекам - не чаще раза в год.
- Несовместимость хотя бы одной подсистемы -> поднять 2-ю цифру. Случайная несовместимость или новые функции в
  3-й/4-й цифре -> отозвать релиз и перевыпустить.
- Выделить программный интерфейс и скрыть остальное; интерфейс и поведение только расширять. Совместимость важнее
  стандартов об именах/синонимах и названиях процедур.
- К программному интерфейсу относятся: экспорт области «Программный интерфейс» (имена, параметры, поведение),
  все экспортные процедуры переопределяемых модулей, имена ролей и элементов стиля, имена объектов метаданных
  (реквизиты, ТЧ), к которым разрешено обращаться из кода и запросов.
- Допустимо в 3-й цифре: новая функция, новая процедура в переопределяемом модуле, необязательный параметр в конец,
  новый реквизит. В 4-й цифре новое API и параметры недопустимы. Изменение поведения при тех же имени и параметрах =
  несовместимость (только 2-я цифра).
- Каждую несовместимость описывать в сопроводительной документации с инструкцией по адаптации (что переименовано,
  удалено, куда перенесено, что добавить в переопределяемый модуль).
- Программный интерфейс размещать в общих модулях, а не в модулях объектов/менеджеров/наборов записей.
- Интерфейс и служебный код - в разных областях или разных модулях; служебный модуль может иметь постфикс
  `Служебный` (`Internal`), например `ОбменСообщениями` / `ОбменСообщениямиСлужебный`.
- Методы для конкретных потребителей - в области `ДляВызоваИзДругихПодсистем` (`InterfaceImplementation`) внутри
  `ПрограммныйИнтерфейс`, сгруппированы комментариями с именем потребителя:
```bsl
#Область ПрограммныйИнтерфейс
// ...
#Область ДляВызоваИзДругихПодсистем
// СтандартныеПодсистемы.ГрупповоеИзменениеОбъектов
// ...
// Конец СтандартныеПодсистемы.ГрупповоеИзменениеОбъектов
#КонецОбласти
#КонецОбласти
```
- Переименование/удаление экспортного метода: старый оставить, пометить комментарием `// Устарела: Следует
  использовать ...` (`Deprecated`), перенести в область `УстаревшиеПроцедурыИФункции` (`Deprecated`) внутри
  `ПрограммныйИнтерфейс`; там допустимы отступления от прочих стандартов. В документации - чем заменить.
- Даже исправление ошибки, меняющее поведение (в т.ч. недокументированное, например возврат `Неопределено` вместо
  исключения), лучше делать новой функцией, а старую помечать устаревшей.
- Новые параметры - только необязательные в конец; при многих параметрах предусмотреть последний параметр-Структуру.
  То же для переопределяемых процедур (`ПриОпределенииНастроек(Настройки)`): новые свойства/события не требуют
  пустых заглушек у потребителей.
- Давать потребителям API вместо прямых запросов к таблицам библиотеки; если API ещё нет - временная функция в
  прикладном коде, которую потом заменить.
- API размещать в обычном общем модуле, а не в `ПовтИсп`/`ВызовСервера` (их держать служебными): тогда реализацию
  можно перенести без изменения точки вызова. То же для переопределяемых модулей.
- Для контроля изменений API есть приложенная к стандарту обработка.

### std668 Разработка ролей в библиотеках - [its](https://its.1c.ru/db/v8std/content/668/hdoc)
Стандарт; все виды приложений.
- В библиотеку - только объекты, которые войдут в потребителей как есть или переопределёнными; специфичное для
  конфигурации создаётся при внедрении.
- Как правило, библиотека поставляет готовые роли для своих объектов с данными. Исключения: подчинённые объекты
  (присоединённые файлы - доступ через роли владельца), заготовки под существенное переопределение (`Организации`,
  `ФизическиеЛица`), библиотеки без данных.
- RLS в библиотечных ролях проектировать так, чтобы потребитель использовал его без правок. Исключения при внедрении:
  в решении нет RLS - удалить тексты ограничений; доступ настраивается по прикладным сущностям - дописать RLS или
  не поставлять роли.
- Для всех ролей библиотеки правило поставки «Изменения разрешены» (роли неявно меняются при добавлении/удалении
  метаданных).

### std690 Обработчики обновления информационной базы - [its](https://its.1c.ru/db/v8std/content/690/hdoc)
Стандарт; управляемое и обычное приложение; для конфигураций на БСП (см. документацию «Обновление версии ИБ»).

Сведения о библиотеке:
- Каждая библиотека и основная конфигурация сообщают имя, версию, список обработчиков, зависимости - в общем модуле
  с именем на `ОбновлениеИнформационнойБазы...` (например, `ОбновлениеИнформационнойБазыУТ`).
- Все такие модули перечислить в `ПодсистемыКонфигурацииПереопределяемый.ПриДобавленииПодсистем`
  (`МодулиПодсистем.Добавить("ОбновлениеИнформационнойБазыУТ")`). Порядок добавления задаёт порядок обработчиков
  при отсутствии/цикле зависимостей.
- Модуль по шаблону: область `ПрограммныйИнтерфейс` с процедурами `ПриДобавленииПодсистемы(Описание)` (Имя, Версия
  из 4 чисел, `ТребуемыеПодсистемы`, `РежимВыполненияОтложенныхОбработчиков` = "Последовательно" | "Параллельно"),
  `ПриДобавленииОбработчиковОбновления`, `ПередОбновлениемИнформационнойБазы`, `ПослеОбновленияИнформационнойБазы`,
  `ПриПодготовкеМакетаОписанияОбновлений`, `ПриОпределенииРежимаОбновленияДанных`,
  `ПриДобавленииОбработчиковПереходаСДругойПрограммы`, `ПриЗавершенииПереходаСДругойПрограммы`; затем область
  `СлужебныеПроцедурыИФункции` с подразделами «Заполнение пустой ИБ» и «Обновление ИБ».
- Обработчики нужны для дозаполнения после реструктуризации: новые константы/реквизиты, перенос из устаревших
  структур, генерация данных. Строки, записываемые в ИБ, - по std784.

Описание обработчика (`ПриДобавленииОбработчиковОбновления`):
```bsl
Обработчик = Обработчики.Добавить();
Обработчик.Версия = "3.1.2.15";            // "*" - при каждом обновлении
Обработчик.Процедура = "Справочник.Склады.ЗаполнитьТипСклада";
Обработчик.РежимВыполнения = "Отложенно";  // "Монопольно" (по умолчанию) | "Оперативно" | "Отложенно"
```
- `Версия` - формат Р.П.В.С; если следующая версия неизвестна - следующий номер сборки. `"*"` - обязательный
  обработчик каждого обновления (служебные данные, профили доступа). Без версии - обязательно
  `НачальноеЗаполнение = Истина` (запуск на пустой ИБ «0.0.0.0»).
- `Монопольно`: без сеансов, заданий, внешних соединений - иначе обновление прерывается; для небольших данных,
  нужных до входа пользователей. Если есть хоть один монопольный - все оперативные тоже выполняются монопольно.
  Для `"*"` ставить монопольный только если обработчик сам решает: первый вызов с
  `Параметры.МонопольныйРежим = Ложь` - ничего не менять, при необходимости выставить Истина и выйти; второй вызов
  (Истина) - менять данные.
- `Оперативно`: при работающих пользователях; редко, для исправительных релизов без изменения структуры данных.
- `Отложенно`: в фоне после входа пользователей; для больших объёмов (архивы, закрытые периоды, неактивные данные).
  При параллельном режиме - следовать стандарту «Параллельный режим отложенного обновления».

Расположение:
- Обработчик - экспортная процедура в модуле менеджера обновляемого объекта. Если объект не определить - в серверном
  общем модуле по смыслу (например, `СкладСервер`), в служебной части, подраздел «Обновление ИБ».

Реализация:
- Никакого интерактива с пользователем.
- Не прерываться, не зацикливаться, не оставлять необработанное, не требовать действий пользователя: неуникальный
  номер - присвоить свободный; битая ссылка - пропустить или взять значение по умолчанию.
- Параллельные отложенные - не бросать исключения. Остальные - только при критической ошибке, когда обходов нет
  (иначе ИБ не запустится).
- Идемпотентность: повторный запуск даёт тот же результат, без дублей.
- В пределах одной версии не зависеть от порядка выполнения; зависимые - объединить в один.
- В подчинённых узлах РИБ с отборами данные могут быть неполными (движения без регистратора) - пропускать такие.
- Работать быстро: отключить бизнес-логику (`ОбменДанными.Загрузка = Истина` или флаг в `ДополнительныеСвойства`)
  и регистрацию на узлах обмена (кроме создания ссылочных объектов, которые должны уйти в РИБ с той же ссылкой).
```bsl
// БСП 2.1.4+: вместо Объект.Записать()
ОбновлениеИнформационнойБазы.ЗаписатьДанные(ДокументОбъект);
// без БСП: Загрузка = Истина; ДополнительныеСвойства "ОтключитьМеханизмРегистрацииОбъектов";
//          ОбменДанными.Получатели.АвтоЗаполнение = Ложь; затем Записать()
```
- Перед процедурой - комментарий: первая строка `// Обработчик обновления <Конфигурация> <версия>`, далее - какие
  данные меняются и как.
- При постановке на поддержку новой версии библиотеки увеличить номер версии конфигурации (иначе обработчики не
  запустятся).

### std705 Отнесение объектов библиотек к подсистемам - [its](https://its.1c.ru/db/v8std/content/705/hdoc)
Стандарт; управляемое и обычное приложение.
- Все объекты библиотеки - в одной корневой подсистеме без командного интерфейса (для БСП - `СтандартныеПодсистемы`).
- Дополнительно допустимы корневые подсистемы с командным интерфейсом.

### std739 Размещение сведений о настройках подсистемы - [its](https://its.1c.ru/db/v8std/content/739/hdoc)
Стандарт; управляемое и обычное приложение.
- Настройки, общие для всех/группы объектов подсистемы, - в переопределяемом модуле, одной процедурой
  `ПриОпределенииНастроек(Настройки)`, где `Настройки` - Структура, заранее заполненная умолчаниями (расширяется
  без потери совместимости).
- Список подключённых объектов не вычислять перебором метаданных с `Попытка ... Исключение` - отдельная процедура
  переопределяемого модуля с явным перечнем (вида `ПриОпределенииПодключенныхОтчетов`).
- Переопределение бизнес-логики для всех объектов - тоже в переопределяемом модуле, отдельная процедура на каждое
  действие, имя по действию.
- Настройки конкретного объекта - в модуле его менеджера, процедура `ПриОпределенииНастроек<ИмяПодсистемы>`
  (например, `ПриОпределенииНастроекВариантовОтчетов`). Объектные обработчики - там же, по процедуре на действие;
  их наличие объявляется флагом в этих настройках, а не проверкой через `Попытка`.
```bsl
// Модуль менеджера отчета
Процедура ПриОпределенииНастроекВариантовОтчетов(Настройки) Экспорт
	Настройки.ПриПолученииДанныхОтчета = Истина; // объявляем, что обработчик ниже есть
КонецПроцедуры
```
