## Организация работы конфигурации (продолжение)

### std680 Поддержка толстого клиента, управляемое приложение, клиент-сервер - [its](https://its.1c.ru/db/v8std/content/680/hdoc)
Стандарт (п.3 - методическая рекомендация); управляемое и обычное приложение.
- Код модулей менеджера, объекта и сеанса обычно рассчитан только на сервер (зовет серверные общие модули).
  Но в толстом клиенте (управляемое приложение, клиент-сервер) они могут скомпилироваться на клиенте: объект
  создан в клиентском коде или платформа неявно зовет обработчики менеджера/сеанса на клиенте. Это дает ошибки
  и замечания проверки конфигурации.
- Поэтому весь код этих модулей обернуть в препроцессор:
```bsl
// Модуль объекта / набора записей
#Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда
// ... весь код модуля
#Иначе
ВызватьИсключение НСтр("ru = 'Недопустимый вызов объекта на клиенте.'");
#КонецЕсли
```
  - модуль сеанса и модули менеджеров всех видов - то же условие, без ветки `#Иначе`.
- Следствие обертки менеджера: в толстом клиенте (управляемое, клиент-сервер) `ОбработкаПолученияПредставления`
  и `ОбработкаПолученияПолейПредставления` не вызываются - представление будет стандартным.
  `ОбработкаПолученияДанныхВыбора` и `ОбработкаПолученияФормы` всегда на сервере - их это не касается.
- (Рек.) Если нужно снять это ограничение: вынести эти два обработчика за препроцессорную обертку, подписки на
  них положить в клиент-серверные модули; серверную работу делать через модуль `...ВызовСервера` без передачи
  мутабельных значений. Не ставить массово флаг «Вызов сервера» всем серверным модулям.
- Для расстановки оберток есть приложенная к стандарту обработка.

### std704 Использование определяемых типов - [its](https://its.1c.ru/db/v8std/content/704/hdoc)
Стандарт; управляемое и обычное приложение.
- Назначение: тип (набор типов) часто используемой сущности или такой, что вероятно меняется при внедрении;
  задается один раз и используется в реквизитах, ресурсах, реквизитах форм, макетах.
- Применять:
  - простой тип с квалификаторами и прикладным смыслом, используемый во многих местах - одинаковые длина и
    точность (`НомерСчетаФактуры` - Строка 30, `АдресДоставки` - Строка 500);
  - составной тип, массово используемый в подсистеме (`КонтактВзаимодействий` = ФизическиеЛица, Партнеры,
    КонтактныеЛицаПартнеров) - иначе при внедрении пришлось бы снимать объекты с поддержки;
  - во встраиваемой подсистеме - для прикладного типа, уточняемого при внедрении (`Поставщики` -> `Контрагенты`).
- Неправильно: «синоним» существующего типа, подмена сущности, локальное применение без потребности во
  внедрении, тип из одного справочника «на всякий случай» - признак ошибки проектирования.

### std706 Ограничения на переименование объектов метаданных - [its](https://its.1c.ru/db/v8std/content/706/hdoc)
Стандарт (п.3 - методическая рекомендация); управляемое, мобильное, обычное приложение.
- Запрещено переименовать общий модуль и создать новый с прежним именем. Делать новый модуль с новым именем и
  переносить код. Иначе при сравнении/объединении с поставкой ссылки (например, из подписок на события)
  свяжутся по имени с новым модулем, где нужных процедур нет.
- Если объект нужно удалить и создать заново с тем же именем (например, сокращение измерений регистра) -
  старый переименовать с префиксом `Удалить`. Иначе у потребителя, менявшего объект с сохранением поддержки,
  старый не удалится и обновление БД упадет из-за двух объектов с одним именем. См. удаление устаревших
  объектов.
- (Рек.) Хранение ссылок на объекты метаданных:
  - без БСП - строковый реквизит (Строка, 255) с полным именем объекта; при переименовании/удалении объектов
    заменять сохраненные имена в обработчике обновления ИБ;
  - с БСП - ссылка на справочник `ИдентификаторыОбъектовМетаданных` (сам отслеживает переименования,
    удаления, добавления; ссылка компактнее строки). Исключение: роли и подсистемы - их переименования
    описывать явно (см. документацию БСП), иначе старый элемент помечается на удаление, создается новый, и
    пропадают варианты отчетов в разделах, доп. отчеты в разделе, роли в профилях групп доступа;
  - `ИдентификаторыОбъектовМетаданных` не для объектов чужих конфигураций (интеграции) - там строки и свой
    механизм актуализации.
  - При параллельных ветках (например, 2.0 и 3.0 или исправительные + плановые релизы) переименование с
    созданием одноименного объекта и двойное переименование делать только в самой старшей версии - иначе при
    переходе со младшей на старшую переименование применится дважды. С `ИдентификаторыОбъектовМетаданных`
    запрет касается только ролей и подсистем.

### std709 Технология разветвленной разработки конфигураций - [its](https://its.1c.ru/db/v8std/content/709/hdoc)
Методическая рекомендация; управляемое, мобильное, обычное приложение. Применимо к хранилищу конфигурации в
Конфигураторе.
- Термины: плановая версия (существенное развитие, срок заранее); исправительная версия (срочные исправления
  критичных ошибок, новая функциональность - только в исключительных случаях, например законодательство);
  технический проект (задание с четкой целью и конечным списком изменений). Учет проектов и ошибок - в СППР.
- Исправительные версии:
  - для каждой - НОВОЕ хранилище из конфигурации последней выпущенной версии (не копировать основное);
  - без объемных доработок (иначе пересмотреть срок плановой версии);
  - каждая закладка (помещение) - с комментарием, по правилам основного хранилища;
  - все изменения синхронно повторять в основном хранилище; новые объекты/реквизиты переносить только
    сравнением/объединением, чтобы совпали внутренние идентификаторы;
  - при сборке ставить метку с номером сборки на версию хранилища, которая идет в сборку (обычно последнюю).
- Плановая версия - в основном хранилище:
  - каждое помещение переводит конфигурацию из одного готового к выпуску состояния в другое; недоотлаженное не
    помещать; хранилище всегда «не развалено»;
  - в основном хранилище допустимы: мелкие исправления без перепроектирования (крупные - отдельным тех.
    проектом), встраивание новых версий библиотек, встраивание отлаженных проектов, в исключительных случаях
    сами проекты (массовый рефакторинг);
  - комментарий обязателен: ошибка - номер и краткое название в баг-трекере; библиотека - название и точная
    версия; встраивание проекта - номер и название; работа по проекту прямо в основном - номер, название и что
    изменено;
  - проект переносится в основное хранилище одним помещением; нужно несколько - открывать несколько проектов;
  - после переноса можно чинить наведенные проектом ошибки; пересмотр решений - новый проект;
  - метка с номером сборки - как для исправительной.
- Технические проекты:
  - каждый - в отдельном хранилище (СППР может создать сам; вручную - Приложение 1);
  - хранилище проекта стоит на поддержке основного; правило «Объект поставщика редактируется с сохранением
    поддержки» включать точечно только на изменяемое (только форму, если меняется лишь форма); для смены
    правил захватывать только корень конфигурации;
  - обновлять хранилище проекта от основного с удобной ответственному частотой (чаще, если задеты чужие
    объекты, идет рефакторинг общих механизмов или массовые исправления) - Приложение 2;
  - сроки тестирования и встраивания согласовать (в СППР - контрольные точки); крупные проекты вносить ближе к
    концу цикла; вносить только после отладочного тестирования, сохранив файл сравнения проекта с основным;
  - не держать объекты основного хранилища захваченными долго: сначала итеративно подтянуть проект до
    основного (может занять дни), после каждой итерации быстро проверить; захватывать в основном, когда
    разница почти равна изменениям проекта;
  - после переноса - совместная с тестировщиками быстрая проверка смежной функциональности;
  - перед помещением - проверка конфигурации с максимальными настройками; помещать только после исправления
    всех внесенных проектом ошибок;
  - после переноса хранилище проекта удалить.
- Номер сборки (4-е число версии, см. std483) увеличивать и в основном, и в исправительном хранилище:
  - непосредственно перед сборкой релиза (полный номер должен отличаться от предыдущего);
  - при помещении обработчика обновления ИБ (с БСП - чтобы у всех разработчиков он запустился после
    обновления из хранилища). Обработчик и новый номер - в одном помещении, обработчик привязан к этому
    номеру. Обработчик из тех. проекта - номер повышается в основном при переносе; исправление в одном
    хранилище - повышать там, в двух - в обоих;
  - если обработчики разбиты по технологическим подсистемам (как в ERP: УправлениеПредприятием и
    УправлениеТорговлей) - повышать номер и подсистемы, и конфигурации;
  - менять в свойствах конфигурации и (с БСП) в `ОбновлениеИнформационнойБазы<ИмяБиблиотеки>.ПриДобавленииПодсистемы`.
- Приложение 1 - создание хранилища проекта: обновить базу основного хранилища - выгрузить файл поставки
  `.cf` - загрузить в базу проекта (встанет на поддержку без изменения) - создать хранилище в общей папке -
  завести пользователя `ТолькоПросмотр` (без пароля и права захвата, только для получения конфигурации) -
  завести участников (логин = фамилия, без пароля, с правом захвата).
- Приложение 2 - подтянуть хранилище проекта (ХТП) до основного (ОХ):
  1. обновить базу ОХ; 2. сделать файл поставки ОХ; 3. захватить все объекты в ХТП;
  4. сравнить основную конфигурацию с конфигурацией поставщика, сохранить отчет о сравнении (текст и табличный
     документ) - это изменения проекта;
  5. Поддержка - Обновить конфигурацию из файла шага 2; в фильтре включить «Показывать только дважды
     измененные свойства» - их объединять внимательно, остальное можно без проверки;
  6. при «Выполнить»: новым объектам поставщика - «Объект не редактируется» (и для «Изменения разрешены», и
     для «Изменения не рекомендуются»), прочим - «Сохранять текущий режим»;
  7. повторно внести затертые доработки проекта;
  8. снова сравнить и сохранить отчет (в другой файл);
  9. сравнить отчеты шага 4 и шага 8 - при правильном обновлении различий нет.

### std723 Особенности разработки конфигураций для ОС Linux и macOS - [its](https://its.1c.ru/db/v8std/content/723/hdoc)
Стандарт; управляемое и обычное приложение.
- Обычно специальных мер не нужно; правила - для частных случаев (приложение 7 документации платформы).
  Ключевые функции реализовывать кроссплатформенными средствами платформы.
- Не использовать COM (`COMОбъект`): администрирование кластера - через ras и `АдминистрированиеСервера`
  вместо `v83.ComConnector`; рабочие каталоги - `РабочийКаталогДанныхПользователя`, `КаталогДокументов`,
  `КаталогВременныхФайлов`; прочее - например, внешние компоненты Native API.
- Поставляемые внешние компоненты (клиент и сервер) - только по технологии Native API (кроссплатформенно,
  включая веб-клиент).
- Объект `Почта` заменять на `ИнтернетПочта` или на компоненты для почтовых клиентов Linux/macOS.
- Картинки WMF/EMF заменить растровыми (PNG, JPG).
- Файлы: в Linux имена регистрозависимы - одно и то же имя писать в одном регистре везде; разделитель пути и
  маску «все файлы» не хардкодить - `ПолучитьРазделительПути()`, `ПолучитьМаскуВсеФайлы()`; с БСП - функции
  `ОбщегоНазначения` / `ОбщегоНазначенияКлиент`.
- Второстепенные сервисные функции (прямое подключение к другим программам, импорт из сторонних почтовых
  клиентов) на Linux/macOS можно отключать: скрывать команды, а если нельзя - сообщение вида «<Операция>
  доступна только при работе в ОС Windows». С БСП - `ЭтоLinuxКлиент`, `ЭтоMacOSКлиент`, `ЭтоWindowsКлиент`.
```bsl
&НаКлиенте
Процедура ОбработкаКоманды(ПараметрКоманды, ПараметрыВыполненияКоманды)
	Если Не ОбщегоНазначенияКлиент.ЭтоWindowsКлиент() Тогда
		ПоказатьПредупреждение(, НСтр("ru = 'Выгрузка в Excel через COM доступна только при работе в ОС Windows.'"));
		Возврат;
	КонецЕсли;
	// ...
КонецПроцедуры
```

### std731 Требования к установке и обновлению прикладных решений - [its](https://its.1c.ru/db/v8std/content/731/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Дистрибутивы установки и обновления готовить по главе 30 «Поставка и поддержка конфигурации» руководства
  разработчика.
- Путь шаблона: `<Каталог шаблонов>\<каталог разработчика>\<каталог конфигурации>\<каталог версии>`; в
  каталоге версии точки заменяются подчеркиваниями (`1C\Trade\11_1_3_6\`).
- В каталоге версии - манифест `1cv8.mft` с описанием шаблонов `.cf` и демо-баз `.dt` (ключи `Vendor`,
  `Name`, `Version`, `AppVersion`, секции `[ConfigN]` с `Catalog`, `Destination`, `Source`).
- В `Catalog` (часть до «/») явно указывать разработчика («1С:Управление торговлей» или «Управление торговлей
  (1С)»); `Destination` = `<каталог разработчика>\<каталог ИБ>`, имя разработчика адаптировано под имя каталога.
- Название разработчика (для шаблонов и для каталогов) глобально уникально, выбирается один раз и используется
  для всех его решений.
- Обновления - отдельные дистрибутивы с `.cfu`. Основной способ - Конфигурация - Поддержка - Обновить
  конфигурацию (поиск файлов обновления); с БСП - подсистема «Обновление конфигурации».

### std759 Несущественные предупреждения проверки конфигурации - [its](https://its.1c.ru/db/v8std/content/759/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Можно не исправлять (не влияют на работу, методики поиска нет): «Пустой обработчик» (для обработчиков
  оповещений), неразрешимые ссылки на объекты метаданных (в формах и справке), неразрешимые ссылки на картинки
  (в формах), неправильные пути к данным (в формах).
- При регламентной проверке НЕ включать «Поиск использования синхронных вызовов» - выдает и корректные места
  (например, серверный код, не исполняемый в веб-клиенте).

### std785 Версия платформы 1С:Предприятие для разработки - [its](https://its.1c.ru/db/v8std/content/785/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Минимальная версия платформы: для решений госучреждений, оборонки, корпоративных клиентов и любых библиотек -
  не выше версии, на которой основан последний сертифицированный релиз «1С:Предприятие 8.3z» (номер
  публикуется на online.1c.ru); в остальных - на усмотрение ответственного. Пример: сертифицирован 8.3.14.2032
  на базе 8.3.14.1976 - минимальная 8.3.14.1976.
- Повышать минимальную можно, если ошибку платформы не обойти в коде (для госсектора - с быстрой сертификацией
  нового релиза). В исправительных релизах библиотек повышать минимальную НЕЛЬЗЯ.
- Рекомендуемая версия: в прикладных - на усмотрение ответственного, ориентир - последний релиз, на котором
  разрабатывают и тестируют; в исправительных релизах библиотек повышать нельзя. Для госсектора рекомендуемая
  может быть выше сертифицированной.
- Запуск ниже минимальной блокирует БСП; минимальная и рекомендуемая задаются в
  `ОбщегоНазначенияПереопределяемый.ПриОпределенииОбщихПараметровБазовойФункциональности`. Обе версии
  также указывать в `readme.txt` дистрибутива.

### std798 Использование ботов системы взаимодействия - [its](https://its.1c.ru/db/v8std/content/798/hdoc)
Стандарт; управляемое приложение.
- Для ботов нужно регламентное задание, вызывающее `СистемаВзаимодействия.ВыполнитьОбработкуБотов()`. Метод
  работает без учета разделителей, по одному системному процессу (WebSocket) на каждую зарегистрированную
  область с ботами; предопределенные боты создаются при первом вызове.
- Для 1cFresh (модель сервиса): не делать предопределенных ботов - дать настройку включения/отключения,
  создавать бота программно при включении и удалять при выключении.
- Регламентное задание с `ВыполнитьОбработкуБотов()` - одно на конфигурацию (сколько бы ни было объектов
  `БотСистемыВзаимодействия`) и неразделенное (не входит ни в один разделитель). Иначе лишняя нагрузка на
  сервер 1С и сервер взаимодействия.
- Бота создавать от пользователя системы взаимодействия, не связанного с пользователем ИБ - иначе этот
  пользователь ИБ потеряет доступ к системе взаимодействия.
- Несколько экземпляров бота одного объекта метаданных - каждому свой пользователь СВ, иначе работает только
  последний созданный.
- `ОбработкаСообщенияСистемыВзаимодействия` не должен выпускать необработанные исключения: сообщение при
  ошибке остается в очереди и повторяется, и если ошибка постоянная - очередь встает навсегда.

## Учет версий конфигураций

### std482 Заполнение свойств конфигурации информацией о выпуске - [its](https://its.1c.ru/db/v8std/content/482/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.

| Свойство | Значение |
|----------|----------|
| Синоним | официальное название + «, редакция N.N» («Бухгалтерия предприятия, редакция 1.6») |
| Имя | из синонима по правилам имен, без слова «редакция» и номеров (`БухгалтерияПредприятия`) |
| Краткая информация | = синоним |
| Подробная информация | = синоним |
| Логотип | для типовых 1С не заполняется |
| Заставка | картинка поддерживаемого формата; размер - по документации |
| Авторские права | `Copyright (C) <разработчик>, ГГГГ-ГГГГ. Все права защищены.` (англ.: `All rights reserved.`), годы выпуска конкретные |
| Адрес информации о поставщике | для 1С: `https://www.1c.ru` |
| Адрес информации о конфигурации | для 1С: `https://v8.1c.ru/<англ. короткое имя>/` |
| Поставщик | для 1С: `Фирма "1С"` |
| Версия | полный номер, например `1.6.4.7` (std483) |
| Адрес каталога обновлений | для 1С: `https://downloads.v8.1c.ru/tmplts/` |

- (Примечание дайджеста, не из стандарта) Для собственных конфигураций подставлять своего разработчика и свои адреса по тому же шаблону.

### std483 Нумерация редакций и версий - [its](https://its.1c.ru/db/v8std/content/483/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Новая редакция - следующее целое число после предыдущей; редакция пишется с подредакцией через точку (1.5,
  1.6); новые конфигурации начинают с 1.0.
- Все версии подредакции (альфа, ознакомительные, бета, финальные) нумеруются подряд с 1.
- Свойство «Версия» = `Р.П.З.С`: редакция, подредакция, версия, сборка; каждое поле - минимум одна цифра,
  можно больше. `1.6.4.7` - сборка 7 версии 4 редакции 1.6. Правила увеличения сборки - std709.

### std484 Общие сведения о выпуске конфигураций - [its](https://its.1c.ru/db/v8std/content/484/hdoc)
Стандарт; управляемое, мобильное, обычное приложение.
- Выпуск идет версиями и редакциями.
- Версия: исправления и мелкие улучшения; переход с предыдущей версии обязан сохранять данные.
- Редакция: существенные изменения структуры учета с преобразованием данных (формальный, но необязательный
  признак - перенос через конвертацию). Переход с сохранением данных желателен; если невозможен - описать
  процедуру перехода (начало работы, перенос начальных остатков и т.п.).
